# 顔をほぼ 100% 隠すための計画

現状の顔隠しは YuNet 単体の毎フレーム検出と、見失ったときの hold で成り立っている。
正面顔にはよく当たるが、横顔・後頭部・遮蔽・ブレ・小さい顔で落ちる。落ちたフレームは
素顔のまま書き出される。この文書は、その取りこぼしを実用上ゼロに近づけるための段取りを
まとめたもの。

数値は断りのない限り**見積り**であり、この素材で測ったものではない。測る手順は 3 節に書いた。
「効果が大きい」と書いてある施策も、測るまでは仮説にすぎない。**この文書の主張のうち、
実測に裏打ちされているのは 2 節（現状のコードの欠陥）だけ**で、そこは実際に計算して確かめてある。

---

## 0. 最初に：「100% 検出」は達成できない

顔検出器の再現率を 100% にする方法は存在しない。後頭部は原理的に「顔」ではないし、
真っ暗なフレームには手がかりが無い。単一の検出器の精度を追う限り、この計画は失敗する。

**目標を「検出率」から「被覆率」に置き換える。**

- 被覆率 = 頭の画素が**マスクの不透明部分で**覆われていたフレーム ÷ 頭が写っているフレーム
- 検出できなかった頭も、位置を推定して覆えれば被覆できる
- どうしても推定できないフレームは、**全画面をぼかす／その区間を捨てる**という逃げ道を用意する

この置き換えをすると、被覆率 100% は設計上到達可能になる。代わりに払うのは
「隠しすぎ（過剰マスク）」と「処理時間」で、どちらも顔バレより安い。

定義について、3 つ先に釘を刺しておく。**この 3 つを外すと、以降の全部が空回りする。**

1. **単位は「顔」ではなく「頭」。** 後頭部を覆いたいなら、測る対象も後頭部を含んでいなければ
   ならない。顔検出器で正解データを作ると、後頭部は正解に入らず、後頭部対策の効果が
   測定上ゼロになる（3.2 節）
2. **覆ったかどうかはアルファで判定する。** 実際に隠しているのは箱ではなく PNG の
   不透明画素（`overlay.py:70-73`）。箱が頭を含んでいても、そこが透明なら顔は見えている
3. **100% を担保するのは C-2（覆えないフレームの処置）と人手であって、検出の改善ではない。**
   検出の改善は「C-2 と人手の出番を減らす」ためにやる

以下、施策を段階 0〜D に分ける。**段階 0 は既存の欠陥を直すだけで、コード 100 行未満。
段階 A 以降に手を付ける前に、ここで取れる分を取り切る。**

## 1. 現状の弱点（構造）

コードに即して並べる。

| # | 弱点 | 該当箇所 |
| --- | --- | --- |
| 1 | **単一パスで、未来の情報を使っていない**。フレームを読みながらその場で検出・合成しているので、「この後 5 フレーム先で顔が再検出される」ことを知らないまま hold の位置を描いている | `render.py:239-250` |

## 2. 現状の欠陥（バグ・結合）

1 節が「無いもの」なのに対して、こちらは「あるが間違っているもの」。
**実際に計算して確かめた。段階 0 で直す。**

### 2.1 画面端で顔が露出する（`faces.py:105-126`）

`FaceBox.expanded()` の `bounds` クランプ。1920x1080・`scale: 2.0` で計算した結果：

| 顔の位置 | 本来覆うべき x 範囲 | 実際に覆う x 範囲 | 症状 |
| --- | --- | --- | --- |
| x=10, w=80（左端） | -30 〜 130 | **0 〜 160** | 箱ごと右へ 30px 平行移動 |
| x=-30, w=80（一部画面外） | -70 〜 90 | **0 〜 160** | 70px 右へずれる |
| x=1870, w=80（右端） | 1830 〜 1990 | 1830 〜 1920（**幅 90px**） | マスク画像が横方向に圧縮される |

- 左・上端では**マスクが顔から離れる方向に平行移動する**。`offset_y` を負にしている人
  （README が「髪が多いなら -0.1」と勧めている）は上端で顎が出る
- 右・下端では `composite()` が `cv2.resize()` するので、**マスク画像そのものが歪む**。
  丸いステッカーが縦長の楕円になり、2.2 と合わせて顔の左右端が透明領域に落ちる
- そして `composite()`（`overlay.py:55-61`）は `src_x0 = max(0, -x0)` で
  **すでに画面外を正しくクリップしている**。このクランプは不要な上に有害

人がフレームに入る／出る瞬間は画面端で起きるので、頻出する漏れ経路。
**`bounds` 引数と 4 行のクランプを削除して `composite()` に任せる。**

### 2.2 マスクの透明部分から顔が見える

隠しているのは箱ではなく PNG のアルファ（`overlay.py:70-73`）。README は透過 PNG を
推奨しているので、丸・星型のステッカーを `scale: 2.0` の箱に貼ると四隅は透明のまま。
YuNet の箱は目鼻口の狭い箱なので、2.0 倍にしても内接円で覆えるのは顔幅の約 1.0 倍分。
**額の生え際・顎・耳が、箱の中にありながら透明領域に落ちる。**

しかもこれは**検出が成功しているフレームで起きる漏れ**なので、この計画の施策
（補間・追跡・骨格）は 1 つも効かない。

**`load_mask()` で実効被覆比（アルファ > 128 の画素比と、内接する最大不透明矩形）を
計算し、起動時に警告する。** 「この mask.png の実効被覆は 61% です。`scale` を 2.6 以上に
することを推奨」と出せば、今日から効く。

### 2.3 カット判定とマスクで `detect_width` が共有されている（`pipeline.py:75`）

閾値はカット用（`cut.face_score_threshold`）とマスク用（`mask.score_threshold`）に
分かれているが、**`detect_width` は `mask` のものをカット判定が読んでいる**。
B-1 でマスク側の解像度を上げると、カット結果まで変わる（顔が見つかる区間が増える＝
カットが減る）。**`cut.detect_width` を分離する。**

### 2.4 YuNet のランドマークを捨てている（`faces.py:149-152`）

```python
FaceBox(float(row[0]), float(row[1]), float(row[2]), float(row[3]), float(row[-1]))
```

`row` は 15 要素で、`row[4:14]` に右目・左目・鼻先・右口角・左口角の座標が入っている。
**無料で手に入る情報を捨てている。** これがあれば：

- **両目から面内回転が直接求まる**。B-2 の「±25° 回転 TTA を全フレームに掛ける」が
  不要になり、「傾いた顔を検出できたとき、次フレームでその角度を優先的に試す」で済む。
  TTA のコストが桁で変わる
- **鼻と両目の相対位置からヨーが粗く求まる**。横を向き始めた顔を検知して、箱を
  向いている方向に非対称へ広げられる。YuNet の箱は目鼻口基準なので、真横では
  後頭部側が足りない。これは一様 2.0 倍の拡大では埋まらない体系的な漏れ
- **検出器間の箱定義の正規化**（B-3）が、両目間距離という共通の物理量でできる
- **トラックの照合**が中心距離だけより安定する（`overlay.py:106-111` の最近傍照合は
  2 人が交差すると入れ替わる）

### 2.5 その他

- **`detect_every_n_frames` と `hold_sec` が結合している。** `hold_frames` は出力フレーム
  単位で計算される（`render.py:205`）が、`tracker.update()` は `local_index % step == 0`
  のときしか呼ばれない（`render.py:241-243`）ので、`missed` は検出回数でしか増えない。
  `3` にすると実効 hold は 0.7 秒ではなく 2.1 秒。安全側に外れるので実害は小さいが、
  B-6 の段階化で同じ罠を踏む
- **`overlay.py:124-130` の分岐が両方同一。** `if detections:` と `else:` が同じ式で、
  実質 `held_frames` のカウント専用。しかも `render.py:244-245` が同じことを別に数えている。
  **意図を汲んで「検出があるときは hold 中のトラックを描かない」に直すと再現率が下がる。**
  現状は意図せず安全側に倒れているので、A-1 で `MaskTracker` を廃止するまで触らない
- **`report.frames_no_face` が無制限に伸びる**（`render.py:266`）。人が写っていない 10 分の
  素材で 18000 個の float。`report.py:72` は 500 件で打ち切って書き出すが、メモリ上は全部持つ。
  C-1 で精査するなら、時刻リストではなく**区間**に畳むべき

## 3. 測れるようにする

施策より先にこれをやる。ここを飛ばすと以降の判断が全部あてずっぽうになる。
**そして、測定の設計を間違えると、正しい施策が数字によって却下される。**

### 3.1 指標

| 指標 | 定義 | 扱い |
| --- | --- | --- |
| 漏れフレーム数 | 頭が写っているのにアルファで覆われていないフレーム | 主指標。最小化 |
| 最長漏れ | 漏れが連続した最長フレーム数 | 主指標 |
| 被覆率 | 頭の箱の画素のうちアルファ > 128 で覆われた割合が 0.95 以上のフレームの比 | 参考 |
| **過剰マスク率** | 頭が無い領域を覆っている画素の比 | **制約**。上限を超えたら評価を fail |
| 要目視時間 | 要確認と報告された区間の合計秒数 | 全長の 5% 以下 |
| 処理時間 | 実時間に対する倍率 | 上限を先に決める |

**過剰マスク率を「参考値」にしてはいけない。** 片側だけを最適化する指標系は必ず退化解に
収束する。全画面ブラーは漏れ 0 で主指標が満点になる。人がツマミを回していく過程で、
じわじわそこに向かう。**制約下での漏れ最小化**として問題を定義すること。上限値は
「顔以外が隠れて映像が成立しなくなる線」から逆算して決める（8 節の決めごと）。

### 3.2 正解データ — 検出器で作ってはいけない

**擬似正解を顔検出器で作る設計は破綻する。** 正解データに含まれるのは「その検出器が
顔だと思ったもの」だけなので、後頭部・真横・強遮蔽の頭はどんなに重いアンサンブルを
積んでも入らない。すると：

- B-5（骨格推定）を入れる前：後頭部で漏れている → 分母に入らない → 被覆率 100%（実際は漏れている）
- B-5 を入れた後：後頭部を覆った → 正解に無い位置を覆った → **過剰マスクが増えただけに見える**

**この評価基盤は、最も高価な施策を「効果ゼロ・コスト増」と判定する。**

正しくはこうする。

1. **アノテーションの単位は「頭」。** 顔ではなく頭。後頭部にも箱を引く。
   これを引けるのは人間だけで、自動化できない
2. **人手でやる。範囲を狭くするために素材を短くする。** 全フレームは無理なので、
   **難所を 3〜5 秒の窓に切り詰め、その窓だけ全フレームに箱を引く**。
   窓を長くして自動で埋めるのは間違い。窓を短くするのが正しい
3. **検出器の出力は「正解」ではなく「アノテーションの初期値」。** D-3 の枠焼き込み出力を
   下敷きにして、間違っているところだけ人が直す。JSON を直接編集で足りる

評価素材は難所を意図的に含める（横を向く／後ろを向く／手で顔を触る／逆光／
奥に離れて小さくなる／速く動く／複数人が交差する）。うまくいくケースを集めても意味がない。
**撮影そのものが 1 日仕事**なので、工数に数えておく。

`tests/make_fixtures.py` の合成素材は工程の検証には使えるが、検出の難しさを再現していない
ので、評価には実写を使う。

### 3.3 この評価セットで言えること／言えないこと

3〜5 本 × 3〜5 秒の窓を数個で、合計 1000〜2000 フレーム。一方、実運用は 10 分＝18000 フレーム。

**1000 フレームで漏れ 0 でも、5000 フレームに 1 回の漏れは検出できない。**
この評価セットで区別できるのは「難所での漏れ率が数 % か、1% 未満か」程度で、
目標の「0」とは桁が違う。

したがって：

- 評価セットの役割は「**難所での漏れ率を比較する、開発用の物差し**」
- 「漏れ 0」の担保は評価セットではなく、**C-2（覆えないフレームの機械的な処置）と
  人手の最終確認**が負う

この区別を曖昧にすると、「評価で 0 だった」を「出荷して安全」と読み替える事故が起きる。

### 3.4 物差しに最初に通すもの

**施策の実装ではなく、既存パラメータのスイープ。**

```
tamako eval --dataset eval/ --sweep mask.score_threshold=0.2,0.3,0.4,0.5 \
                            --sweep mask.detect_width=640,960,1280
```

これで、以降の全ての施策が「何に対する追加分か」というベースラインを持つ。
段階 A 以降の効果は、**ゼロに対してではなく、このスイープ後の値に対して**測る。

## 4. 段階 0 — 既存の欠陥を直し、設定を振る

**コード 100 行未満。段階 A に手を付ける前に、ここで取れる分を取り切る。**

| # | 内容 | 触る箇所 |
| --- | --- | --- |
| 0-1 | `expanded()` の端クランプを削除（2.1） | `faces.py`, `render.py` |
| 0-2 | `mask.png` の実効被覆比を起動時に警告（2.2） | `overlay.py` |
| 0-3 | `cut.detect_width` を分離（2.3） | `config.py`, `pipeline.py` |
| 0-4 | 書き出しを k フレーム遅延させ、箱に**時間方向の max フィルタ**を掛ける | `render.py` |
| 0-5 | `score_threshold` と `detect_width` を振って目視で比較 | 設定のみ |

### 0-4 時間方向の max フィルタ

書き出しを 15 フレーム（0.5 秒）遅延させるリングバッファを入れ、各フレームの箱集合を
**前後 ±15 フレームの箱集合と合わせる**（それぞれ描く）。

- **二段化なしで双方向の被覆が手に入る。** 等速仮定も、破綻判定も、パラメータも要らない
- 1080p × 15 枚で約 90MB
- `MaskTracker` の hold は残したまま、その出力に後段として掛けるだけ

A-2（双方向補間）と A-4（オプティカルフロー）が狙う効果のかなりの部分が、これで取れる
可能性がある。**どれくらい取れるかは測るまで分からない。** 重要なのは、
**A-2/A-4 の追加投資を、ゼロに対してではなくこの max フィルタとの差分に対して
正当化する**こと。段階 A の設計を、この実測より先に確定させない。

### 0-5 パラメータのスイープ

**計画に「閾値を下げる」という施策が無かったのは欠落だった。**

- **`mask.score_threshold`: 0.5 → 0.2〜0.3。** `FaceDetectorYN` の既定 0.9 より下げてはあるが、
  マスク用途としてはまだ高い。**マスクは false positive のコストがほぼゼロ**（過剰マスク＝
  安全側）なので、precision を捨てて recall を買うのが正しい設定。設定ファイルの数字 1 つ
- **`mask.detect_width`: 640 → 1280。** YuNet が検出できる最小顔は入力画像上で概ね 10〜20px。
  1080p で顔幅 40px（引きの画では普通）は 640px 縮小後に 13px で境界線上、
  480px（README がトラブルシュートで勧めている値）では 10px で消える。1280 に上げるだけで
  この帯域が戻る。計算量は 4 倍だが YuNet はもともと軽い

**段階 A の補間・追跡は「一度検出された顔の周辺のギャップ」しか埋められない。
一度も検出されない顔（小さい顔、常に横向きの人）には原理的に無力。**
先に検出の底上げをしないと、段階 A は自分の効果を半分しか出せない。

## 5. 段階 A — 構造を変える

段階 0 の実測を見てから設計を確定する。追加依存は無い。

### A-1 二段化：解析パスと描画パスを分ける

顔検出を書き出しから切り離し、先に全フレーム分を走らせて中間ファイルに落とす。

```
faces.jsonl  {"clip": "a.mp4", "pts": 40.133, "boxes": [[x, y, w, h, score], ...],
              "landmarks": [[...], ...]}
```

**仕様で先に決めておくこと（決めないと確実に事故る）：**

- **座標系は素材のピクセル座標。** 描画パスは `fit_filters()`（`frames.py:42-65`）で
  `scale` + `pad` した出力ジオメトリでフレームを読む。縦横比の違う素材が混ざると
  レターボックスのオフセット分ずれる。**描画時に scale+pad を適用して変換する**
- **キーはフレーム番号ではなく PTS（秒）。** 描画パスは区間ごとに `-ss` で入力シークする
  （`frames.py:87-88`）ので、クリップ通しの frame index と `-ss` + `fps=` 後の local_index が
  一致する保証がない。**ギャップの端で 1 フレームずれることは、そのまま 1 フレームの顔バレ**

**得られるもの：**

- 未来のフレームの検出結果を使える（A-2 の前提）
- **手動オーバーライドの受け皿ができる**（A-6。ここが本命）
- 検出をやり直さずにマスクの大きさ・位置だけ調整して再書き出しできる
- **`scan_face_presence` を廃止して統合できる。** 現在は `pipeline.py:68` の 3fps 走査と
  `render.py:242` の毎フレーム検出で、顔検出が 2 回走っている。解析パスで全フレーム
  検出すれば、カット判定用の顔在区間もそこから導出できる

**速度は初回だけ遅くなる。** 二段化するとフルレートのデコードが 1 回から 2 回に増える。
`scan_face_presence` の統合で一部相殺されるが、初回実行は遅くなる。再書き出しは速くなる。
**両方書いておく。**

`MaskTracker` は書き換えではなく**廃止**する。ストリーミング構造では双方向補間は
書けないので、ギャップ埋めは `faces.jsonl` 上のオフライン後処理（`tracks.py`）になる。

### A-2 双方向の補間

ギャップの前後に検出があるなら、その間の位置は推定できる。ただし段階 0-4 の max フィルタと
比べた追加分がどれだけあるかは、測ってから判断する。

**設計上、以下を守る：**

- **x, y, w, h を全部補間する。** 人が奥から手前に歩けば箱は大きくなる
- **拡大量はギャップ長ではなく「速度 × 時間」に比例させる。** 位置推定の誤差は時間だけでは
  増えない。静止している人の 2 秒ギャップに拡大は要らず、速いパンの 3 フレームギャップには
  大きな拡大が要る。`拡大量 = max(下限, k × |v| × Δt)`。**前後の速度が食い違うほど
  （＝等速仮定が破れているほど）拡大を増やす**と、失敗モードそのものを不確かさに変換できる
- **「和集合」は外接矩形ではなく「両方の箱をそれぞれ描く」。** 離れた 2 箱の外接矩形を取ると、
  間の何も無い領域を丸ごと覆う（画面端から端に移動していたら画面全体）
- **拡大に上限を設け、超えたら C-2 のポリシーに送る。** 上限が無いと、10 秒のギャップで
  顔幅の 10 倍以上を覆うことになる
- **シーンチェンジを跨いで補間しない。** クリップ内の場面転換を跨ぐと、マスクが瞬間移動して
  両方の位置で漏れる。フレーム間差分か ffmpeg の `select='gt(scene,0.4)'` で境界を出し、
  そこでは補間を禁止する。**A-2 の前提条件**

**線形補間の弱点を正しく認識しておく。** 検出が落ちるのは、人が振り向いた・急に動いた・
カメラが振れた瞬間である。**つまり線形補間が最も外れる状況でしか、線形補間は使われない。**
これが、段階 0-4 の単純な max フィルタが健闘しうる理由でもある。

### A-3 端点の外挿

片側にしかアンカーが無い場合。直前の速度で外挿し、外挿した秒数に比例して箱を広げる。
上限を超えたら C-2 の判断に回す。

### A-4 オプティカルフローでギャップを埋める（優先度：低）

`cv2.calcOpticalFlowPyrLK` で箱の内側の特徴点を追う。**実装コストは「小」ではない。**
実務水準にするには以下が要る。

- **前方後方誤差（forward-backward error）**。t→t+1 で追った点を t+1→t で追い戻し、
  元の位置とのずれが大きい点を捨てる。これが無いと遮蔽物に乗り移った点を検出できない。
  `status` と `err` を両方使い、変位は平均でなく**中央値**で取る
- **スケール変化の推定。** LK は平行移動しか出さない。箱の拡縮は、生き残った点集合の
  **ペア間距離の中央値の比**から相似変換を推定する必要がある。これが無いと、カメラに
  近づく人の箱が小さいまま置き去りになる
- **外部整合性チェック。** 顔検出が落ちる理由の代表が「手で顔を触る」で、そのとき箱の中の
  最も強い特徴点は**手**にある。LK は素直に手を追い、マスクが手と一緒に画面外へ去っていく。
  前方後方誤差ではこれを捕まえられない（手は一貫して追えているため）。
  **LK の変位が A-2 の補間位置から乖離したら LK を捨てる**
- **顔は低テクスチャで、ブレるとテクスチャがゼロになる。** `goodFeaturesToTrack` が拾えるのは
  目・鼻孔・生え際・眼鏡くらい。**ブレたフレームでは LK は原理的に破綻する。**
  つまり A-4 は A-2 が最も外れる状況（ブレ）で同様に外れる。この 2 つは冗長ではなく、
  同時に失敗する
- 後方向のフローには未来のフレームが要る。段階 0-4 のリングバッファに乗る

**代案：** 箱の追跡には CSRT/MOSSE のような相関フィルタ系のほうが、スケール推定と信頼度が
組み込みで付いてくる分だけ素直。`opencv-python-headless` → `opencv-contrib-python-headless`
の差し替えは `requirements.txt` の 1 行で、新しいライブラリを増やすわけではない。
「追加依存なし」を理由に LK を選ぶ前に、この中間案を検討する。

### A-5 トラックの再結合

長いギャップの前後を「同一人物」と繋げるかどうかの判断。

**照合特徴は顔の箱ではなく胴体の色を使う。** 顔の箱の中身は肌と髪なので、
**人が違ってもほぼ同じヒストグラムになり、人物照合に使えない。** 顔箱の下方向に
オフセットした胴体領域（服の色）なら、同一シーン内では極めて強力な特徴になる。
実装コストは同じ。ここを間違えると「A-5 は効かなかった」という誤った結論が出る。

繋がらないなら、両方を独立のトラックとして扱い、**どちらも覆う**（安全側）。

### A-6 手動オーバーライド ← 100% への唯一の経路

`faces_manual.jsonl` を同じ形式で受け取り、描画時に自動検出結果と union でマージする
（人手が常に勝つ）。人が「この時刻に、この箱」を 2 点書けば、その間はキーフレーム補間で埋まる。

**9 節で「自動では 100% を保証できない」と書いている以上、100% への経路はこれしかない。**
段階 D（見つける）と対になる「直す」手段が無いと、確認作業は「漏れを見つけたので設定を
変えて全部やり直し」で終わる。

**GUI は要らない。** JSON を手で書ける形式にして、D-2 の抜き出し動画に時刻とフレーム番号を
焼き込めば足りる。A-1 で中間ファイルを作るなら、追加は 100 行程度。

## 6. 段階 B — 検出の再現率そのものを上げる

段階 0・A を入れて評価し、まだ残る漏れの性質に応じて選ぶ。**全部やる必要はない。**
そして、**残った漏れの内訳（後頭部 / 小顔 / 暗所）を正しく分類できるのは、
3.2 の人手アノテーション（頭ラベル）がある場合だけ。**

### B-1 検出解像度とタイル分割

段階 0-5 で `detect_width` は上げてあるので、ここでは残りを扱う。画面内で顔が極端に
小さい素材（引きの画）が多いなら、**タイル分割検出**（重なりを持たせて 2×2 に割り、
各タイルを検出して統合）。全解像度検出と近い効果を、より安く得られることが多い。

### B-2 入力側の TTA（テスト時変換）

**2.4 のランドマークを先に使うこと。** 両目から面内回転が求まるので、
「全フレームに ±25° を掛ける」ではなく「傾いた顔を検出できたら次フレームでその角度を
優先する」で済み、コストが桁で変わる。

そのうえで残る TTA：

- **CLAHE / ガンマ補正**：暗所・逆光。人の目には見えている顔が、検出器には潰れている
- **左右反転**：モデルの偏りを打ち消す。効果は小さめ

B-6 と組み合わせて、必要なフレームだけに掛ける。

### B-3 検出器のアンサンブル

弱点の異なる検出器を並べる。**ただし統合方法を間違えると、再現率を上げる目的で入れた
アンサンブルが再現率を削る。**

| 候補 | 長所 | 短所・注意 |
| --- | --- | --- |
| SCRFD（insightface / onnxruntime） | 横顔・小顔・遮蔽に強い | 依存が重い。**学習済みモデル（buffalo 系）は非商用研究用途に限定**。要確認 |
| MediaPipe Face Detection | 導入が軽い。Apache-2.0 | YuNet と弱点が似ており、上積みが小さい可能性 |
| YOLO 系顔検出 | 再現率が高い | Ultralytics は AGPL-3.0。配布形態次第で影響が出る |

**統合方法（ここが重要）：**

- **NMS を使わない。NMS は箱を削除する演算で、削除は必ず被覆を減らす方向にしか働かない。**
  正しくは**クラスタリング＋外接矩形**（重なる箱をまとめて全体を包む）。
  マスクにとって「大きめ」は常に正解。表示用の箱を作っているわけではない
- **スコアをそのまま比較しない。** YuNet と SCRFD と MediaPipe のスコアは別の学習で得た
  別のシグモイド出力で、0.7 という数字に共通の意味はない。スコア順に処理すると
  **系統的にスコアの高い検出器が常に勝つ**。評価素材で各検出器の「スコア s のときの
  precision」を測って共通尺度に写す（等分位変換で十分）
- **IoU で「同じ顔か」を判定しない。** YuNet の箱は目鼻口だけの狭い箱、SCRFD は額と顎を含む
  広い箱、頭部検出はさらに大きい。**同じ顔に対して IoU が 0.3 を切ることがある。**
  中心距離 + サイズ比、または 2.4 のランドマーク（両目間距離）で正規化する

### B-4 頭部検出

CrowdHuman の head 注釈で学習した頭部検出モデルを使う。
「人物検出をして人物枠の上部を頭とみなす」は粗く、人が屈む・座る・手を上げると
枠の上端が頭でなくなるので、B-5 が使えるならそちらを採る。

### B-5 骨格推定から頭を推定する

姿勢推定は**顔の見た目ではなく体の構造**から関節位置を出す。後ろを向いていても肩・首は
見えているので、体の配置から頭の位置を割り出せる。**失敗の仕方が顔検出と補完的**なのが効く。

| 状況 | 顔検出 | 骨格推定 |
| --- | --- | --- |
| 後頭部・真横 | ✗ | ○ |
| 顔が小さい（引きの画） | ✗ | ○（体は大きく写っている） |
| 顔だけ遮蔽（手・マスク・髪） | ✗ | ○ |
| 極端な寄りで肩が画面外 | ○ | ✗ |
| 人が重なる | ○ | △（骨格が混ざることがある） |
| **暗所・ブレ・小ささ** | ✗ | **✗〜△** |

**最後の行が重要。補完的ではあっても独立ではない。** 暗所・ブレ・小ささは両方を同時に殺す。
C-1 でこれを忘れると危険（7.1 節）。

**頭の箱をつくる（下ほど頑健）：**

1. 頭部キーポイント（鼻・両目・両耳）の外接矩形を拡大する
2. 肩から推定する。肩の中点から、肩を結ぶ線に垂直な方向へ進んだ位置を頭の中心とする
3. 両方が得られたときは両方を描く

**大きさの手がかりの選び方（当初案から修正）：**

人が横を向くと**肩幅は画像上で縮む**（両肩を結ぶ線がカメラを向くため）。横向きこそ
隠したい場面なので、これは放置できない。当初は「胴の長さ（肩の中点↔腰の中点）は
垂直軸まわりの回転で縮まない」を対策としていたが、**これは主用途では使えない**：

- 前傾・後傾、着座、カメラの高さによる短縮では普通に縮む
- **腰が画面に入っていないと計算できない。** この道具の主用途（話している人を撮る）は
  バストショットが中心で、腰は写っていないのが普通

**したがって、実際に効くのは「そのトラックの直近の頭の大きさ」。**
頭サイズを緩やかな状態変数として持ち、不確かなときは単調に大きくする。
胴長の機構を作り込むより、こちらのほうが実装も判断も簡単で堅牢。

**肩線が縮退したときのガード：** ヨーが 90° に近いと両肩がほぼ同じ画像座標に来て、
肩線の方向が数ピクセルの誤差で 180° 回る。**頭を肩の下に置く。**
画素単位の肩幅が閾値を下回ったら、垂線ではなく「画像上の上方向 + 直近の相対位置」に落とす。

**個体較正の自己矛盾（当初案の誤り）：**

「顔検出が成功しているフレームで顔サイズと肩幅の比を実測する」——しかし
**顔検出が成功しているのは正面を向いているとき**であり、その比を適用したいのは
横を向いているとき。**横向きでは肩幅が縮む、というのがこの節の出発点だった。
較正は、直そうとしたバイアスをそのまま継承する。**

較正するなら、対象を回転に強い量（頭サイズ / 頭-肩距離）にするか、
「そのときの肩幅」ではなく時間的に滑らかな深度代理に対して取る。
**較正はクリップを跨いで持ち越さない**（ズーム・カメラ移動・カットで無効になる。
`render.py:236` が区間ごとに tracker を作り直しているのと同じ理由）。

**モデル選定の注意：**

- **旧来の `mp.solutions.pose`（`pip install mediapipe` で最も普通に使われる API）は
  単一人物専用**で、画面内で最も目立つ 1 人しか返さない。多人数には新しい
  `PoseLandmarker` Tasks API を `num_poses > 1` で使う必要があり、**フレーム間の ID 追跡は
  自前**。評価素材に「複数人が交差する」を入れている以上、ここを外すと複数人シーンで
  1 人だけ覆われて残りが素通しになる
- 候補：MediaPipe Pose（導入が軽い）、RTMPose（精度が高いが依存が重い）、
  YOLO 系 pose（AGPL-3.0）。**モデルごとにライセンスが違う**ので「MediaPipe だから
  Apache-2.0」と一括りにしない
- mediapipe は protobuf / numpy をピン留めするので、既存の opencv + numpy 構成と
  衝突しうる。`setup.bat` で 1 発で入る保証はない
- 人物らしい形（ポスター・人形・鏡像）にも骨格が出る。過剰マスクは安全側なので許容

**隠れた工数：** 骨格トラックと顔トラックの対応付け（多人数の跨フレーム ID 管理）が
丸ごと必要になる。これは B-5 本体と同規模の追跡問題。

### B-6 段階的な計算（速度対策）

**安い検出を毎フレーム、高い検出は必要なフレームだけ**に限る。

```
毎フレーム        YuNet（現状のまま）
  ↓ 何も出なかった／トラックが途切れた／確信度が低い フレームだけ
2 段目            解像度を上げる・TTA・アンサンブル
  ↓ それでも出ない
3 段目            頭部検出・骨格推定
  ↓ それでも出ない
                  段階 C へ
```

**前提が成り立つ範囲に注意。** 「大多数は 1 段目で終わる」は簡単な素材でしか成り立たない。
**難しいフレームが 3 割ある素材（＝この計画が対象にしている素材）では、平均コストは
緩和されない。** 2.5 の `detect_every_n_frames` と同じ結合の罠も踏まないこと。

**C-3 との関係：** ラダーの最上段と C-3 の検査器を同じにしてはいけない（7.3 節）。

## 7. 段階 C — 最終防衛線

**「ほぼ 100%」を名乗れるかどうかは、ここで決まる。**

### 7.1 C-1 「人は居るのに顔が無い」フレームを見つける

顔が無いフレームには 2 種類ある。

- **本当に誰も写っていない**（風景・手元・物撮り）→ 何もしなくてよい
- **人は写っているが顔を取れていない** → 危険

**「骨格も顔も無ければ人は写っていない」と判断してはいけない**（当初案の誤り）。
姿勢推定は暗所・強い遮蔽（机の陰で頭と肩しか出ていない座り姿勢＝この道具の主用途）・
フレーム端で半分切れている人・小さい人物・ブレで普通に落ちる。**顔検出と骨格推定は
補完的ではあっても独立ではなく、暗所・小ささ・ブレは両方を同時に殺す**（B-5 の表の最終行）。
両方の陰性を陽性の証拠として扱い、しかも「何もしない」に倒れるのは、この計画の中で唯一
**負の検出結果を根拠に保護を放棄する**箇所だった。

**顔も骨格も無いフレームは「判定不能」とし、C-2 のポリシーに送る。**

**判定材料に音声を使う。** `silence.py` がすでに無音区間を計算している。
**「音が鳴っている（喋っている）のに顔も骨格も無い」は、人が写っている強い証拠。**

- 追加依存ゼロ、計算コストゼロ（既に計算済み）
- **視覚検出器と完全に独立したモダリティ**なので、「検出器の弱点が相関する」問題
  （7.1・7.3 の根本原因）を回避できる唯一の手がかり
- これだけでも、該当区間を最優先の要確認として報告する価値がある

### 7.2 C-2 覆えないフレームの扱い ← 段階 A で実装する

```jsonc
"mask": {
  //   expand : 推定できる範囲を大きめに覆う（既定）
  //   blur   : 画面全体をぼかす（確実だが見た目が悪い）
  //   cut    : そのフレームを出力から落とす
  //   warn   : 何もせず報告だけする（現状の動作）
  "uncovered_policy": "expand"
}
```

**`blur` と `cut` を選べば漏れフレームは定義上ゼロになる。
これが漏れ 0 を数学的に保証する唯一の施策であり、0 節の主張の全重量を担っている。**

**したがって段階 B に依存させてはいけない。** 実装は「マスクが 1 つも出ていないフレーム」
または「推定だけで描いているフレーム」に `cv2.GaussianBlur` を掛けるか、フレームを落とすだけ。
`render.py` の 10 行で、段階 A の時点で書ける。

（人物領域だけをぼかせば見た目の劣化は減るが、そのためにセグメンテーションの依存を
増やす価値があるかは、`blur` が実際に使われる頻度を測ってから判断する。）

### 7.3 C-3 出力の再検査 — 位置づけを訂正する

書き出した `edited.mp4` を再度検出器に掛ける施策。当初「自動 QA として最も価値がある」と
書いたが、**保証できる範囲を取り違えていた。**

**論理的な穴：**

1. **検査器と本番の検出器が同じなら、検査は原理的に空振りする。** フレーム N で本番の
   検出器が失敗したから漏れたのであり、同じ画素を同じ検出器に見せれば同じく失敗する。
   検査の価値は「検査器の再現率 − 本番の再現率」の差分だけ。**B-6 のラダー最上段と
   C-3 の検査器を同じにすると、定義上何も見つからない**
2. **除外ルールが、最頻の漏れ方を握り潰す。** 実務で最も多い漏れは完全な未検出ではなく
   **部分被覆**（箱がずれた・小さかった、2.2 のアルファ、2.1 の端バグ）。部分被覆された顔の
   検出箱は当然マスク位置と重なるので、「マスク位置と重なるものを除外」は
   **部分被覆を狙い撃ちで消す**。隣にいる別人の顔も消える
3. **部分被覆はそもそも顔検出で検知できない。** 目だけ隠して顎と口が出ている顔は
   検出されないことが多いが、人間には誰か分かる。**顔検出は「識別可能性」の代理指標として
   不適切**
4. **検査が何も出さなかったとき、「漏れが無い」のか「検査器が見えていない」のかを
   区別する情報がない**

**保証されること／されないこと（ここを明記する）：**

- **保証される：パイプラインの配管ミスの検出。** 座標変換の取り違え、レターボックスの
  オフセット、A-1 のフレームずれ、`expanded()` の端バグ、マスク PNG の読み込み失敗、
  エンコード段での取りこぼし。**回帰テストとしては優秀**
- **保証されない：検出の再現率に関することは一切。** 「出力に顔が無い」は
  「マスクを貼り忘れていない」以上のことを言わない

**したがって：**

- 位置づけを「被覆率の保証」から**「パイプライン回帰テスト」**に変える。名前も
  `verify` ではなく `selftest` 系にする
- 除外ルールを変える。「マスク位置と重なるものを捨てる」ではなく、
  **重なりが小さい検出＝警告、重なっている検出＝「部分被覆の疑い」として別カテゴリで報告**。
  部分被覆こそ見たいもの
- **検査を顔検出でやるのをやめ、顔認識（埋め込みの距離）でやる**（段階 B 以降）。
  隠したい人物の顔を数枚登録し、出力の各フレームで登録者の埋め込みと一致する領域が
  無いかを見る。これなら「顔検出器は顔と認識しないが人間には識別可能」な部分被覆を
  捕まえられる。**顔認識はトラック結合には不要**（顔が見えている必要があり、
  必要な場面＝後頭部・遮蔽では取れない）だが、この用途には価値がある

## 8. 段階 D — 人の確認を現実的にする

自動で 100% を保証することはできない。**最後は人が見る。**
確認作業を「全編を再生する」から「疑わしい箇所だけ見る」に変える。

- **D-1 コンタクトシート**：危険度の高いフレームを縮小して並べた PNG
- **D-2 確認用の抜き出し動画**：危険な時刻の前後 1 秒だけを繋いだ短い mp4。
  **時刻とフレーム番号を焼き込む**（A-6 の手動オーバーライドを書くのに要る）
- **D-3 検出枠の焼き込み**：マスクの代わりに枠・確信度・**その箱の由来
  （検出 / hold / 補間 / 外挿 / 骨格 / 手動）** を描いた検証用出力。
  **3.2 のアノテーションの下敷きでもあるので、評価基盤より先に作る**
- **D-4 報告の並べ替え**：`edit_report.json` の危険箇所を時刻順ではなく**危険度順**に出す

危険度の目安：判定不能 > 長い外挿 > 骨格からの推定 > 補間 > 確信度が低い検出 > 通常の検出。

### 素顔の中間生成物が新しい漏洩経路になる

- D-1 のコンタクトシート＝**素顔のサムネイルを並べた PNG**
- D-3 の枠焼き込み映像＝**マスクを貼らない素顔の動画**
- 3.2 のアノテーション用出力も同じ
- **`faces.jsonl` 自体が個人情報**（いつ誰がどこにいたかの座標時系列）

プライバシー保護が目的の道具が `output/` に素顔のファイルを生成する。README の運用フローは
「`output\edited.mp4` を確認して人に渡す」なので、`output` フォルダごと渡される。

**専用のサブフォルダ（`output/_review/`）に隔離し、README に警告を書き、
確認完了後に削除するコマンドを用意する。**

## 9. 素材側の運用ルール

**ROI で言えばこれが単独最大で、コストはゼロ。**
アルゴリズムで取り返そうとしている損失の多くは、撮影段階で作られている。

- **シャッタースピードを上げる。** モーションブラーが減り、YuNet の再現率が直接上がる
- **逆光を避け、顔に光を回す**
- **撮影解像度を上げる。** 4K で撮って 1080p に落とせば、検出は 4K 側で走らせられる
- **背景に通行人が入る画角を避ける**
- 自分たちの撮影なら、被写体に「カメラに背を向けない」「顔を手で覆わない」と伝える

エンジニアリング計画としては範囲外だが、目的（顔を隠す）に対しては最も効く。

## 11. 速度への影響

- **A-1 の二段化で、初回実行は遅くなる**（フルレートのデコードが 1 回 → 2 回）。
  `scan_face_presence` の統合で一部相殺される。再書き出しは速くなる
- **B は積み上げると効く。** `detect_width` 1280 で検出 4 倍、B-2 の TTA で 3〜5 倍、
  B-3 のアンサンブルで 2〜3 倍、B-5 の骨格で + 数十 ms/frame。B-6 で緩和するが、
  難しいフレームが多い素材では緩和されない（6 節 B-6）
- **具体的な数字はここに書かない。** 素材と機械で桁が変わるので、3.1 の指標に処理時間を
  含めて実測する。**Windows の CPU 単体で 10 分の 1080p を処理する現実的な上限を先に決めて、
  そこから逆算する**

逃げ道：解析パスを複数プロセスに割る、onnxruntime を GPU 対応にする（Windows なら
DirectML）、`preset` を落とす。

## 12. 設定の追加案

**素の設定項目を増やしすぎると破綻する。** 現在 `mask` は 7 項目で、下の案を全部足すと
18 項目。しかも `detect_scales` × `rotation_tta` × `detectors` はコストが掛け算で増え、
`pose_calibrate` は `pose_fallback` に依存し、`uncovered_policy` は他の全部の結果に依存する。
**README がバッチファイルをダブルクリックする層に向けて書かれている**ことを考えると、
この設定面は使われない。

**プリセットを 1 つだけ表に出す。**

```jsonc
"mask": {
  // normal   : 現状相当

  // paranoid : 覆えないフレームをぼかす。確実だが見た目が犠牲になる
  "safety": "high"
}
```

個別項目は上級者向けとして、プリセットを上書きする形で残す。

## 13. 決めておくべきこと

1. **依存を増やしてよいか**。段階 B の効果は大きいが、`setup.bat` が重くなり、
   ネットワークが塞がれた環境での導入が難しくなる。現状は OpenCV と numpy だけで完結している。
   **#0〜#8 は追加依存ゼロで完結する**ので、この判断は先送りできる
2. **モデルのライセンス**。配り方（個人利用か、公開か、業務か）で使えるモデルが変わる。
   B-3・B-5 の注意書きを参照。**モデル単位で確認する**こと
3. **後頭部・真横を隠す必要があるか**。素材にそれが出るなら B-5 が要る。
   **ただし #3 の人手アノテーション（頭ラベル）が無いと、B-5 の効果は測定できない。**
   B-5 をやるなら、アノテーションもやる
4. **過剰マスク率の上限**（3.1 の制約）。顔以外が隠れて映像が成立しなくなる線。
   これを数値で決めないと、指標系が全画面ブラーに向かって退化する
5. **処理時間の上限**。10 分の 1080p を Windows の CPU 単体で何分までなら許容するか。
   B の積み上げはここから逆算する
6. **カット判定への波及**。顔検出の再現率を上げると `cut.mode: any` での「顔なし」判定が減り、
   カットされる区間が減る（`pipeline.py:68-79`）。閾値は分離されているが
   **`detect_width` は分離されていない**（2.3）。カットは false positive が困り、
   マスクは false negative が困る、という非対称を設定の分離で保つ

## 14. この計画の限界

段階 D まで実装しても、**「見なくてよい」とは言えない**。言えるようになるのは
「見るべき箇所が全長の数 % に絞られ、そこを見れば足りる」までで、README の警告は残す。

C-2 で `blur` か `cut` を選べば漏れフレームは定義上ゼロになるが、それは
「顔が写っているかもしれないフレームを捨てた」だけで、検出できたわけではない。
確実性と映像の質は交換関係にあり、この計画はその交換を**人が選べる形にする**もので、
交換そのものを無くすものではない。

そして、**3.3 で書いた通り、評価セットは「漏れ 0」を証明できない。**
証明できるのは「難所での漏れ率が下がった」ことまで。
「漏れ 0」は C-2 の機械的な処置と、A-6 の人手修正と、最後の目視が担保する。
評価で 0 だったことを、出荷して安全だと読み替えないこと。
