# 顔をほぼ 100% 隠すための計画

現状の顔隠しは YuNet 単体の毎フレーム検出と、見失ったときの hold で成り立っている。
正面顔にはよく当たるが、横顔・後頭部・遮蔽・ブレ・小さい顔で落ちる。落ちたフレームは
素顔のまま書き出される。この文書は、その取りこぼしを実用上ゼロに近づけるための段取りを
まとめたもの。

**完成形は「自動で最大限隠し、残りを人が直せる状態にする」こと**（9 節）。
100% の自動検出は原理的に不可能なので、検出の強化はそこへ至る手段であって目的ではない。
検出を強くするほど人の作業が減る、という関係にある。

数値は断りのない限り**見積り**であり、この素材で測ったものではない。測る手順は 3 節に書いた。
「効果が大きい」と書いてある施策も、測るまでは仮説にすぎない。**この文書の主張のうち、
実測に裏打ちされているのは 2 節（現状のコードの欠陥）だけ**で、そこは実際に計算して確かめてある。

---

## 0. 最初に：「100% 検出」は達成できない

顔検出器の再現率を 100% にする方法は存在しない。後頭部は原理的に「顔」ではないし、
真っ暗なフレームには手がかりが無い。単一の検出器の精度を追う限り、この計画は失敗する。

**目標を「検出率」から「被覆率」に置き換える。**

- 被覆率 = 頭の画素が**マスクの不透明部分で**覆われていたフレーム ÷ 頭が写っているフレーム
- 検出できなかった頭も、位置を推定して覆えれば被覆できる
- どうしても推定できないフレームは、**その区間を捨てる**という逃げ道を用意する
  （**ぼかし・モザイクは使わない**。隠すのは `mask.png` の重ね合わせだけで統一する）

この置き換えをすると、被覆率 100% は設計上到達可能になる。代わりに払うのは
「隠しすぎ（過剰マスク）」と「処理時間」で、どちらも顔バレより安い。

定義について、3 つ先に釘を刺しておく。**この 3 つを外すと、以降の全部が空回りする。**

1. **単位は「顔」ではなく「頭」。** 後頭部を覆いたいなら、測る対象も後頭部を含んでいなければ
   ならない。顔検出器で正解データを作ると、後頭部は正解に入らず、後頭部対策の効果が
   測定上ゼロになる（3.2 節）
2. **覆ったかどうかはアルファで判定する。** 実際に隠しているのは箱ではなく PNG の
   不透明画素（`overlay.py:70-73`）。箱が頭を含んでいても、そこが透明なら顔は見えている
3. **100% を担保するのは C-2（覆えないフレームの処置）と人手であって、検出の改善ではない。**
   検出の改善は「C-2 と人手の出番を減らす」ためにやる。
   **ぼかしを使わない以上、C-2 で機械的に打てる手は「フレームを落とす」だけ**になるので、
   人手（A-6）の比重はさらに大きくなる

**そして、その「人手」を実際に機能させる工程が要る。**
見つけても直せなければ確認は徒労に終わる。9 節がそれを扱う。

以下、施策を段階 0〜D に分ける。**段階 0 は既存の欠陥を直すだけで、コード 100 行未満。
段階 A 以降に手を付ける前に、ここで取れる分を取り切る。**

## 1. 現状の弱点（構造）

コードに即して並べる。

| # | 弱点 | 該当箇所 |
| --- | --- | --- |
| 1 | **単一パスで、未来の情報を使っていない**。フレームを読みながらその場で検出・合成しているので、「この後 5 フレーム先で顔が再検出される」ことを知らないまま hold の位置を描いている | `render.py:239-250` |

## 2. 現状の欠陥（バグ・結合）

1 節が「無いもの」なのに対して、こちらは「あるが間違っているもの」。
**実際に計算して確かめた。段階 0 で直す。**

### 2.1 画面端で顔が露出する（`faces.py:105-126`）

`FaceBox.expanded()` の `bounds` クランプ。1920x1080・`scale: 2.0` で計算した結果：

| 顔の位置 | 本来覆うべき x 範囲 | 実際に覆う x 範囲 | 症状 |
| --- | --- | --- | --- |
| x=10, w=80（左端） | -30 〜 130 | **0 〜 160** | 箱ごと右へ 30px 平行移動 |
| x=-30, w=80（一部画面外） | -70 〜 90 | **0 〜 160** | 70px 右へずれる |
| x=1870, w=80（右端） | 1830 〜 1990 | 1830 〜 1920（**幅 90px**） | マスク画像が横方向に圧縮される |

- 左・上端では**マスクが顔から離れる方向に平行移動する**。`offset_y` を負にしている人
  （README が「髪が多いなら -0.1」と勧めている）は上端で顎が出る
- 右・下端では `composite()` が `cv2.resize()` するので、**マスク画像そのものが歪む**。
  丸いステッカーが縦長の楕円になり、2.2 と合わせて顔の左右端が透明領域に落ちる
- そして `composite()`（`overlay.py:55-61`）は `src_x0 = max(0, -x0)` で
  **すでに画面外を正しくクリップしている**。このクランプは不要な上に有害

人がフレームに入る／出る瞬間は画面端で起きるので、頻出する漏れ経路。
**`bounds` 引数と 4 行のクランプを削除して `composite()` に任せる。**

### 2.2 マスクの透明部分から顔が見える

隠しているのは箱ではなく PNG のアルファ（`overlay.py:70-73`）。README は透過 PNG を
推奨しているので、丸・星型のステッカーを `scale: 2.0` の箱に貼ると四隅は透明のまま。
YuNet の箱は目鼻口の狭い箱なので、2.0 倍にしても内接円で覆えるのは顔幅の約 1.0 倍分。
**額の生え際・顎・耳が、箱の中にありながら透明領域に落ちる。**

しかもこれは**検出が成功しているフレームで起きる漏れ**なので、この計画の施策
（補間・追跡・骨格）は 1 つも効かない。

**`load_mask()` で実効被覆比（内接する最大不透明矩形の比 r）を計算し、描画時に
`scale_eff = scale / r` として自動補正する。** 警告して人に「2.6 以上を推奨」と判断させるのは
不要な意思決定で、判断を挟まず補正するのが正しい。補正した事実はログに出す。
検出が成功しているフレームで起きる漏れなので対象フレーム数が桁違いに多く、
**人手コストゼロで直る改善としては単独で最大**。

### 2.3 カット判定とマスクで `detect_width` が共有されている（`pipeline.py:75`）

閾値はカット用（`cut.face_score_threshold`）とマスク用（`mask.score_threshold`）に
分かれているが、**`detect_width` は `mask` のものをカット判定が読んでいる**。
B-1 でマスク側の解像度を上げると、カット結果まで変わる（顔が見つかる区間が増える＝
カットが減る）。**`cut.detect_width` を分離する。**

### 2.4 YuNet のランドマークを捨てている（`faces.py:149-152`）

```python
FaceBox(float(row[0]), float(row[1]), float(row[2]), float(row[3]), float(row[-1]))
```

`row` は 15 要素で、`row[4:14]` に右目・左目・鼻先・右口角・左口角の座標が入っている。
**無料で手に入る情報を捨てている。** これがあれば：

- **両目から面内回転が直接求まる**。B-2 の「±25° 回転 TTA を全フレームに掛ける」が
  不要になり、「傾いた顔を検出できたとき、次フレームでその角度を優先的に試す」で済む。
  TTA のコストが桁で変わる
- **鼻と両目の相対位置からヨーが粗く求まる**。横を向き始めた顔を検知して、箱を
  向いている方向に非対称へ広げられる。YuNet の箱は目鼻口基準なので、真横では
  後頭部側が足りない。これは一様 2.0 倍の拡大では埋まらない体系的な漏れ
- **検出器間の箱定義の正規化**（B-3）が、両目間距離という共通の物理量でできる
- **トラックの照合**が中心距離だけより安定する（`overlay.py:106-111` の最近傍照合は
  2 人が交差すると入れ替わる）

### 2.5 その他

- **`detect_every_n_frames` と `hold_sec` が結合している。** `hold_frames` は出力フレーム
  単位で計算される（`render.py:205`）が、`tracker.update()` は `local_index % step == 0`
  のときしか呼ばれない（`render.py:241-243`）ので、`missed` は検出回数でしか増えない。
  `3` にすると実効 hold は 0.7 秒ではなく 2.1 秒。安全側に外れるので実害は小さいが、
  B-6 の段階化で同じ罠を踏む
- **`overlay.py:124-130` の分岐が両方同一。** `if detections:` と `else:` が同じ式で、
  実質 `held_frames` のカウント専用。しかも `render.py:244-245` が同じことを別に数えている。
  **意図を汲んで「検出があるときは hold 中のトラックを描かない」に直すと再現率が下がる。**
  現状は意図せず安全側に倒れているので、A-1 で `MaskTracker` を廃止するまで触らない
- **`report.frames_no_face` が無制限に伸びる**（`render.py:266`）。人が写っていない 10 分の
  素材で 18000 個の float。`report.py:72` は 500 件で打ち切って書き出すが、メモリ上は全部持つ。
  時刻リストではなく**区間（サイト）**に畳むべき
- **`low_confidence` はもっと悪い**（`render.py:247-250`）。`low_score_warn: 0.75` 未満の検出を
  1 箱ずつ積むので、段階 0-5 で `score_threshold` を 0.25 に下げると [0.25, 0.75) の周辺検出が
  **全部**入る。**閾値を下げる改善が、危険リストを 18000 行のノイズに変えて人の確認を破壊する。**
  これも区間に畳む
- **設定の未知キー検査が最上位しか見ない**（`config.py:185`）。`_deep_merge` はネストされた
  未知キーを黙って通すので、`"mask": {"score_treshold": 0.25}` という綴り間違いは
  **エラーにならず、無視される**（実際に確認した）。README が「隠し漏れがあったら
  `score_threshold` を下げろ」と指示している＝**この道具で最も打鍵される設定**なので、
  ユーザは直したつもりで直っていない。再帰検査に直すのは 5 行
- **トラック照合が作成順の貪欲マッチ**（`overlay.py:101-117`）。古いトラックから順に最寄りの
  検出を取るので、2 人が交差すると入れ替わり、しかも**入れ替わり先が「たまたま古いほう」に
  固定される**。人手の修正記録が付いた側が別人に化ける（9.5 に効く）。全ペア距離をソートして
  マッチするだけで大幅に改善する（10 行）
- **復号エラーが握り潰される**（`frames.py:105,115`）。途中で切れたフレームは無言で捨てられ、
  stderr が空のまま異常終了すると例外も出ない。**復号が途中で死んでも「短い動画」が正常終了
  として書き出される。** 部分フレームと非ゼロ終了は無条件で例外にする

### 2.6 時間軸の欠陥 — 9 節の前提を壊すので最優先で直す

人手修正の記録は「このフレームのこの位置」を指す。**フレームの同定が曖昧なら、
その上に積む工程は全部ずれる。** コードから確認できる問題が 2 つある。

1. **出力フレームと素材時刻の対応が厳密でない。** `frames.py:87-88` は `-ss` を `-i` の前に
   置き、`fps=` フィルタで整形する。シークの着地点とフィルタの位相は区間ごとに違うため、
   出力フレーム k の素材時刻は `start + k/fps + δ`（δ は区間ごとに異なる、最大 1 素材フレーム）。
   **対処：`-ss` は 2 秒手前への粗いシークに限定し、精密なトリムはフィルタ側
   `trim=start=..:end=..,setpts=PTS-STARTPTS` で行う。** 復号の節約は維持され、
   素材時刻 ↔ 出力フレームの対応が整数で確定する
2. **A/V 同期が区間数に比例してずれる。** 映像は ffmpeg が出したフレーム数をそのまま連結
   （`render.py:268`）、音声は `atrim` の**厳密な秒数**を連結（`render.py:125`）。区間あたり
   最大 1/fps の差が**累積**し、100 区間・30fps なら最悪 3.3 秒。`-shortest` は末尾を切るだけで
   ずれは隠れたまま進む。`make_fixtures.py` の短い素材では顕在化せず、テストをすり抜ける。
   **対処：区間のフレーム数を `round(duration × fps)` で先に確定させ、映像は必ずその枚数を
   出す（不足は最終フレーム複製・超過は捨てる）。音声のトリム長はそこから逆算する。**
   これで `out_frame_index` が唯一の権威になる

この 2 つと、(clip, 素材 PTS) ↔ 出力フレーム番号の変換を 1 箇所に閉じ込める
**`timeline.py`** をセットで入れる。人手記録は必ず素材側の座標で保存し、
表示だけ出力時刻にする。**出力時刻は、素材を 1 本足しただけで意味が変わる
揮発性の識別子**であり、耐久性のある記録に使ってはいけない。

## 3. 測れるようにする

施策より先にこれをやる。ここを飛ばすと以降の判断が全部あてずっぽうになる。
**そして、測定の設計を間違えると、正しい施策が数字によって却下される。**

### 3.1 指標

| 指標 | 定義 | 扱い |
| --- | --- | --- |
| 漏れフレーム数 | 頭が写っているのにアルファで覆われていないフレーム | 主指標。最小化 |
| 最長漏れ | 漏れが連続した最長フレーム数 | 主指標 |
| 被覆率 | 頭の箱の画素のうちアルファ > 128 で覆われた割合が 0.95 以上のフレームの比 | 参考 |
| **過剰マスク率** | 頭が無い領域を覆っている画素の比 | **制約**。上限を超えたら評価を fail |
| 要目視時間 | 要確認と報告された区間の合計秒数 | 全長の 5% 以下 |
| 処理時間（バッチ） | 実時間に対する倍率 | 上限を先に決める |
| **処理時間（対話）** | 人の修正 1 箇所あたりに機械が待たせる時間 | **数秒以内**（9.7） |
| **有効指摘率** | 実際に修正を要したサイト ÷ 提示したサイト | 0.5 以上。低いと人がリストを信用しなくなる |
| **見逃し率** | 提示されなかった漏れサイト ÷ 全漏れサイト | 0 に近づける。無作為監査枠（9.8）でのみ推定可能 |

**「サイト」を先に定義する。** フレーム単位の記録（`frames_no_face` など）は人が見る単位では
ない。連続する危険フレームを 1 つの区間に畳んだものをサイトと呼び、**報告・確認・修正・指標の
すべてをサイト単位で数える**。18000 フレームは畳めば概ね数十サイトになり、それが人の作業量の
実体になる。

**過剰マスク率を「参考値」にしてはいけない。** 片側だけを最適化する指標系は必ず退化解に
収束する。画面全体に `mask.png` を貼れば漏れ 0 で主指標が満点になる。
人がツマミを回していく過程で、じわじわそこに向かう。**制約下での漏れ最小化**として
問題を定義すること。上限値は「顔以外が隠れて映像が成立しなくなる線」から逆算して決める
（14 節の決めごと）。

### 3.2 正解データ — 検出器で作ってはいけない

**擬似正解を顔検出器で作る設計は破綻する。** 正解データに含まれるのは「その検出器が
顔だと思ったもの」だけなので、後頭部・真横・強遮蔽の頭はどんなに重いアンサンブルを
積んでも入らない。すると：

- B-5（骨格推定）を入れる前：後頭部で漏れている → 分母に入らない → 被覆率 100%（実際は漏れている）
- B-5 を入れた後：後頭部を覆った → 正解に無い位置を覆った → **過剰マスクが増えただけに見える**

**この評価基盤は、最も高価な施策を「効果ゼロ・コスト増」と判定する。**

正しくはこうする。

1. **アノテーションの単位は「頭」。** 顔ではなく頭。後頭部にも箱を引く。
   これを引けるのは人間だけで、自動化できない
2. **人手でやる。量は少なくてよい。** 難所を 3〜5 秒の窓に切り詰め、
   **5 フレームおきに引く（合計 300 枚程度）**。連続フレームは互いにほぼ同一なので、
   全フレームに引いても実効標本数はほとんど増えない。正直に 1000〜2000 枚引くと
   5〜11 時間かかり、必ず雑になる。浮いた時間で評価素材をもう 1 本撮るほうが情報量が多い
3. **検出器の出力は「正解」ではなく「アノテーションの初期値」。** D-3 の枠焼き込み出力を
   下敷きにして、間違っているところだけ人が直す。JSON を直接編集で足りる

評価素材は難所を意図的に含める（横を向く／後ろを向く／手で顔を触る／逆光／
奥に離れて小さくなる／速く動く／複数人が交差する）。うまくいくケースを集めても意味がない。
**撮影そのものが 1 日仕事**なので、工数に数えておく。

`tests/make_fixtures.py` の合成素材は工程の検証には使えるが、検出の難しさを再現していない
ので、評価には実写を使う。

**そして、このアノテーションより先に手に入る評価装置がある。** 9.8 で述べる通り、
人手修正のログ（どこを・何回・どう直したか）は、評価セットより広い範囲（実素材の全編）を
測っており、決定に直結し、コストがゼロ。**撮影 1 日＋アノテーション人日を投じる前に、
まず人手工程を 1 本回してログを見る。** アノテーションの目的は「過剰マスク率の測定」と
「見逃し率の推定」に絞る。

### 3.3 この評価セットで言えること／言えないこと

3〜5 本 × 3〜5 秒の窓を数個で、合計 1000〜2000 フレーム。一方、実運用は 10 分＝18000 フレーム。

**1000 フレームで漏れ 0 でも、5000 フレームに 1 回の漏れは検出できない。**
この評価セットで区別できるのは「難所での漏れ率が数 % か、1% 未満か」程度で、
目標の「0」とは桁が違う。

したがって：

- 評価セットの役割は「**難所での漏れ率を比較する、開発用の物差し**」
- 「漏れ 0」の担保は評価セットではなく、**C-2（覆えないフレームの機械的な処置）と
  人手の最終確認**が負う

この区別を曖昧にすると、「評価で 0 だった」を「出荷して安全」と読み替える事故が起きる。

### 3.4 物差しに最初に通すもの

**施策の実装ではなく、既存パラメータのスイープ。**

```
tamako eval --dataset eval/ --sweep mask.score_threshold=0.2,0.3,0.4,0.5 \
                            --sweep mask.detect_width=640,960,1280
```

これで、以降の全ての施策が「何に対する追加分か」というベースラインを持つ。
段階 A 以降の効果は、**ゼロに対してではなく、このスイープ後の値に対して**測る。

### 0-4 時間方向の max フィルタ — 実装先を訂正する

各フレームの箱集合を**前後 ±15 フレーム（0.5 秒）の箱集合と合わせて描く**。
等速仮定も、破綻判定も、パラメータも要らない双方向の被覆。

当初は `render.py` に書き出し遅延のリングバッファとして入れる案だったが、**撤回する**。
理由は 2 つ。

1. **A-1 を入れた瞬間に捨てるコードになる。** `faces.jsonl` の上では、これは 10 行の
   リスト演算にすぎない
2. **`render.py` に書くと、区間内に閉じる。** 各区間の先頭・末尾 15 フレームは片側しか
   参照できず、**カット境界＝ hold も履歴も無い最も弱い箇所で効かない**。
   `faces.jsonl` 上（素材時間軸・カット適用前）なら、境界の前後も連続した文脈で埋まる

ここから一般化して、**不変条件として明文化する**：
**「トラックの後処理（max フィルタ・hold・補間・外挿）はすべて素材クリップの時間軸上、
カット適用前に行う。カットは最後に適用する。」**

役割は変わらない：A-2/A-4 の追加投資は、ゼロに対してではなく
**この max フィルタとの差分に対して**正当化する。

### 0-5 パラメータのスイープ

**計画に「閾値を下げる」という施策が無かったのは欠落だった。**

- **`mask.score_threshold`: 0.5 → 0.2〜0.3。** `FaceDetectorYN` の既定 0.9 より下げてはあるが、
  マスク用途としてはまだ高い。**マスクは false positive のコストがほぼゼロ**（過剰マスク＝
  安全側）なので、precision を捨てて recall を買うのが正しい設定。設定ファイルの数字 1 つ
- **`mask.detect_width`: 640 → 1280。** YuNet が検出できる最小顔は入力画像上で概ね 10〜20px。
  1080p で顔幅 40px（引きの画では普通）は 640px 縮小後に 13px で境界線上、
  480px（README がトラブルシュートで勧めている値）では 10px で消える。1280 に上げるだけで
  この帯域が戻る。計算量は 4 倍だが YuNet はもともと軽い

**段階 A の補間・追跡は「一度検出された顔の周辺のギャップ」しか埋められない。
一度も検出されない顔（小さい顔、常に横向きの人）には原理的に無力。**
先に検出の底上げをしないと、段階 A は自分の効果を半分しか出せない。

## 5. 段階 A — 構造を変える

段階 0 の実測を見てから設計を確定する。追加依存は無い。

### A-1 二段化：解析パスと描画パスを分ける

顔検出を書き出しから切り離し、先に全フレーム分を走らせて中間ファイルに落とす。

```
faces.jsonl  {"clip": "a.mp4", "pts": 40.133, "boxes": [[x, y, w, h, score], ...],
              "landmarks": [[...], ...]}
```

**仕様で先に決めておくこと（決めないと確実に事故る）：**

- **座標系は素材のピクセル座標。** 描画パスは `fit_filters()`（`frames.py:42-65`）で
  `scale` + `pad` した出力ジオメトリでフレームを読む。縦横比の違う素材が混ざると
  レターボックスのオフセット分ずれる。**描画時に scale+pad を適用して変換する**
- **キーはフレーム番号ではなく PTS（秒）。** 描画パスは区間ごとに `-ss` で入力シークする
  （`frames.py:87-88`）ので、クリップ通しの frame index と `-ss` + `fps=` 後の local_index が
  一致する保証がない。**ギャップの端で 1 フレームずれることは、そのまま 1 フレームの顔バレ。**
  2.6 の時間軸契約が前提
- **縮小は Python でやらず ffmpeg 側でやる。** 現行の `render` 内検出は 1080p BGR を
  パイプで受けて（6.2MB/frame、10 分で 112GB）毎フレーム `frame.copy()` と `cv2.resize` を
  している。detect パスにフル解像度の義務はないので、`scale=1280:-2` を ffmpeg 側に置けば
  パイプは 2.8MB/frame、Python 側の resize と copy はゼロになる。
  `scan_face_presence` は既にこの方式であり、同じパターンを適用するだけ
- **クリップ単位で並列化する。初日から。** 入力は通常 10〜30 本のクリップで、検出は
  クリップ間で完全に独立。`multiprocessing.Pool` に投げるだけで 4〜8 コアがほぼ線形に効く
  （ワーカ内は `cv2.setNumThreads(1)`、ffmpeg は `-threads 2`）。12 節の予算が閉じるかどうかは
  ここで決まるので、「逃げ道」ではなく設計項目
- **スキーマは最初から完全にする。** 後から足すと全消費者を書き直す。初日から要るもの：
  `track_id`（内容由来ハッシュ：`hash(clip, 初検出 pts, 量子化した初検出中心)` —
  パラメータを変えても大半が生き残る）、`source`（yunet / interp / extrap / hold / pose /
  manual — D-3 の由来表示と危険度の両方が要求）、`conf`、`uncertainty_radius`
  （A-2 の拡大量の数値記録）。**ファイル先頭にメタ行**：モデル SHA・検出パラメータのハッシュ・
  素材の (mtime, size)。**「検出は 1 回きり」と言うなら、何をもって再検出が要ると判断するかの
  キャッシュ無効化規則がここに要る**。古い `faces.jsonl` で書き出す事故を防ぐ
- **置き場所は `output/` の外（`.tamako_work/`）。** 8 節は `faces.jsonl` を個人情報として
  確認後に削除するとしていたが、9 節の「検出は 1 回きり」と矛盾する（削除したら再検出）。
  `output/` に置くのは人に渡してよいものだけ、とすれば両立する

**得られるもの：**

- 未来のフレームの検出結果を使える（A-2 の前提）
- **手動オーバーライドの受け皿ができる**（A-6。ここが本命）
- 検出をやり直さずにマスクの大きさ・位置だけ調整して再書き出しできる
- **`scan_face_presence` を廃止して統合できる。** 現在は `pipeline.py:68` の 3fps 走査と
  `render.py:242` の毎フレーム検出で、顔検出が 2 回走っている。解析パスで全フレーム
  検出すれば、カット判定用の顔在区間もそこから導出できる

**「二段化で復号が 1 回から 2 回に増える」という以前の記述は誤りだったので訂正する。**
`scan_face_presence` の `fps=3` は ffmpeg のフィルタであり、**復号自体は全フレームに対して
行われている**（間引かれるのは出力だけ）。つまり現状すでにフルレート復号は 2 回走っており
（走査でクリップ全体＋書き出しで残す区間）、A-1 はそれを「detect でクリップ全体＋render で
残す区間」に置き換えるだけで、**復号回数は増えない**。増えるのは YuNet の呼び出し回数のみで、
render からは検出が消えるぶん**速くなる**。再書き出しはさらに速い。
**A-1 のコストは当初の想定より低く、先にやる理由が一つ増えた。**

`MaskTracker` は書き換えではなく**廃止**する。ストリーミング構造では双方向補間は
書けないので、ギャップ埋めは `faces.jsonl` 上のオフライン後処理（`tracks.py`）になる。

### A-2 双方向の補間

ギャップの前後に検出があるなら、その間の位置は推定できる。ただし段階 0-4 の max フィルタと
比べた追加分がどれだけあるかは、測ってから判断する。

**設計上、以下を守る：**

- **x, y, w, h を全部補間する。** 人が奥から手前に歩けば箱は大きくなる
- **拡大量はギャップ長ではなく「速度 × 時間」に比例させる。** 位置推定の誤差は時間だけでは
  増えない。静止している人の 2 秒ギャップに拡大は要らず、速いパンの 3 フレームギャップには
  大きな拡大が要る。`拡大量 = max(下限, k × |v| × Δt)`。**前後の速度が食い違うほど
  （＝等速仮定が破れているほど）拡大を増やす**と、失敗モードそのものを不確かさに変換できる
- **「和集合」は外接矩形ではなく「両方の箱をそれぞれ描く」。** 離れた 2 箱の外接矩形を取ると、
  間の何も無い領域を丸ごと覆う（画面端から端に移動していたら画面全体）
- **拡大に上限を設け、超えたら C-2 のポリシーに送る。** 上限が無いと、10 秒のギャップで
  顔幅の 10 倍以上を覆うことになる
- **シーンチェンジを跨いで補間しない。** クリップ内の場面転換を跨ぐと、マスクが瞬間移動して
  両方の位置で漏れる。フレーム間差分か ffmpeg の `select='gt(scene,0.4)'` で境界を出し、
  そこでは補間を禁止する。**A-2 の前提条件**

**線形補間の弱点を正しく認識しておく。** 検出が落ちるのは、人が振り向いた・急に動いた・
カメラが振れた瞬間である。**つまり線形補間が最も外れる状況でしか、線形補間は使われない。**
これが、段階 0-4 の単純な max フィルタが健闘しうる理由でもある。

### A-3 端点の外挿（A-2 より優先）

片側にしかアンカーが無い場合。直前の速度で外挿し、外挿した秒数に比例して箱を広げる。
上限を超えたら C-2 の判断に回す。

**優先度を A-2 より上げる。** 「画面外に出ていく人を、あと 1 秒だけ覆う」は
人手修正で**最も頻度が高くなる操作**であり、それを数十行の自動処理で消せる。
人の修正回数を減らす、という基準で見ると A-2 の補間より直接的に効く。

### A-4 オプティカルフロー — 採用しない

`cv2.calcOpticalFlowPyrLK` で箱の内側の特徴点を追う案。**採用しない。**
理由：本文の技術的問題に加えて、人手工程の観点で決定的な欠陥がある。
**LK は自信満々に間違った答えを何十フレームも出し続け、自己申告しない。**
漏れと過剰マスクを同時に生み、しかも危険リストに載らない——
「修正しやすい形で失敗する」の真逆で、人手工程と最も相性が悪い。
CSRT などの相関フィルタ系も同じ性質を持つ。

以下は、再検討する場合に踏むべき論点の記録として残す。

- **前方後方誤差（forward-backward error）**。t→t+1 で追った点を t+1→t で追い戻し、
  元の位置とのずれが大きい点を捨てる。これが無いと遮蔽物に乗り移った点を検出できない。
  `status` と `err` を両方使い、変位は平均でなく**中央値**で取る
- **スケール変化の推定。** LK は平行移動しか出さない。箱の拡縮は、生き残った点集合の
  **ペア間距離の中央値の比**から相似変換を推定する必要がある。これが無いと、カメラに
  近づく人の箱が小さいまま置き去りになる
- **外部整合性チェック。** 顔検出が落ちる理由の代表が「手で顔を触る」で、そのとき箱の中の
  最も強い特徴点は**手**にある。LK は素直に手を追い、マスクが手と一緒に画面外へ去っていく。
  前方後方誤差ではこれを捕まえられない（手は一貫して追えているため）。
  **LK の変位が A-2 の補間位置から乖離したら LK を捨てる**
- **顔は低テクスチャで、ブレるとテクスチャがゼロになる。** `goodFeaturesToTrack` が拾えるのは
  目・鼻孔・生え際・眼鏡くらい。**ブレたフレームでは LK は原理的に破綻する。**
  つまり A-4 は A-2 が最も外れる状況（ブレ）で同様に外れる。この 2 つは冗長ではなく、
  同時に失敗する
- 後方向のフローには未来のフレームが要る。段階 0-4 のリングバッファに乗る

**代案：** 箱の追跡には CSRT/MOSSE のような相関フィルタ系のほうが、スケール推定と信頼度が
組み込みで付いてくる分だけ素直。`opencv-python-headless` → `opencv-contrib-python-headless`
の差し替えは `requirements.txt` の 1 行で、新しいライブラリを増やすわけではない。
「追加依存なし」を理由に LK を選ぶ前に、この中間案を検討する。

### A-5 トラックの再結合

長いギャップの前後を「同一人物」と繋げるかどうかの判断。

**照合特徴は顔の箱ではなく胴体の色を使う。** 顔の箱の中身は肌と髪なので、
**人が違ってもほぼ同じヒストグラムになり、人物照合に使えない。** 顔箱の下方向に
オフセットした胴体領域（服の色）なら、同一シーン内では極めて強力な特徴になる。
実装コストは同じ。ここを間違えると「A-5 は効かなかった」という誤った結論が出る。

繋がらないなら、両方を独立のトラックとして扱い、**どちらも覆う**（安全側）。

### A-6 手動オーバーライド ← 仕上げ工程の土台

`faces_manual.jsonl` を `faces.jsonl` と同じ形式で受け取り、描画時にマージする
（人手が常に勝つ）。**A-1 の二段化がそのまま「人が編集できる状態」になる。**

**15 節で「自動では 100% を保証できない」と書いている以上、100% への経路はこれしかない。**
段階 D（見つける）と対になる「直す」手段が無いと、確認作業は「漏れを見つけたので設定を
変えて全部やり直し」で終わる。

**この工程の全体像は 9 節にまとめた。** ここは中間ファイルのマージ規則だけを扱う。

## 6. 段階 B — 検出の再現率そのものを上げる

段階 0・A を入れて評価し、まだ残る漏れの性質に応じて選ぶ。**全部やる必要はない。**
そして、**残った漏れの内訳（後頭部 / 小顔 / 暗所）を正しく分類できるのは、
3.2 の人手アノテーション（頭ラベル）がある場合だけ。**

### B-1 検出解像度とタイル分割

段階 0-5 で `detect_width` は上げてあるので、ここでは残りを扱う。画面内で顔が極端に
小さい素材（引きの画）が多いなら、**タイル分割検出**（重なりを持たせて 2×2 に割り、
各タイルを検出して統合）。全解像度検出と近い効果を、より安く得られることが多い。

### B-2 入力側の TTA（テスト時変換）

**2.4 のランドマークを先に使うこと。** 両目から面内回転が求まるので、
「全フレームに ±25° を掛ける」ではなく「傾いた顔を検出できたら次フレームでその角度を
優先する」で済み、コストが桁で変わる。

そのうえで残る TTA：

- **CLAHE / ガンマ補正**：暗所・逆光。人の目には見えている顔が、検出器には潰れている
- **左右反転**：モデルの偏りを打ち消す。効果は小さめ

B-6 と組み合わせて、必要なフレームだけに掛ける。

### B-3 検出器のアンサンブル

弱点の異なる検出器を並べる。**ただし統合方法を間違えると、再現率を上げる目的で入れた
アンサンブルが再現率を削る。**

| 候補 | 長所 | 短所・注意 |
| --- | --- | --- |
| SCRFD（insightface / onnxruntime） | 横顔・小顔・遮蔽に強い | 依存が重い。**学習済みモデル（buffalo 系）は非商用研究用途に限定**。要確認 |
| MediaPipe Face Detection | 導入が軽い。Apache-2.0 | YuNet と弱点が似ており、上積みが小さい可能性 |
| YOLO 系顔検出 | 再現率が高い | Ultralytics は AGPL-3.0。配布形態次第で影響が出る |

**統合方法（ここが重要）：**

- **NMS を使わない。NMS は箱を削除する演算で、削除は必ず被覆を減らす方向にしか働かない。**
  正しくは**クラスタリング＋外接矩形**（重なる箱をまとめて全体を包む）。
  マスクにとって「大きめ」は常に正解。表示用の箱を作っているわけではない
- **スコアをそのまま比較しない。** YuNet と SCRFD と MediaPipe のスコアは別の学習で得た
  別のシグモイド出力で、0.7 という数字に共通の意味はない。スコア順に処理すると
  **系統的にスコアの高い検出器が常に勝つ**。評価素材で各検出器の「スコア s のときの
  precision」を測って共通尺度に写す（等分位変換で十分）
- **IoU で「同じ顔か」を判定しない。** YuNet の箱は目鼻口だけの狭い箱、SCRFD は額と顎を含む
  広い箱、頭部検出はさらに大きい。**同じ顔に対して IoU が 0.3 を切ることがある。**
  中心距離 + サイズ比、または 2.4 のランドマーク（両目間距離）で正規化する

### B-4 頭部検出

CrowdHuman の head 注釈で学習した頭部検出モデルを使う。
「人物検出をして人物枠の上部を頭とみなす」は粗く、人が屈む・座る・手を上げると
枠の上端が頭でなくなるので、B-5 が使えるならそちらを採る。

### B-5 骨格推定から頭を推定する

姿勢推定は**顔の見た目ではなく体の構造**から関節位置を出す。後ろを向いていても肩・首は
見えているので、体の配置から頭の位置を割り出せる。**失敗の仕方が顔検出と補完的**なのが効く。

| 状況 | 顔検出 | 骨格推定 |
| --- | --- | --- |
| 後頭部・真横 | ✗ | ○ |
| 顔が小さい（引きの画） | ✗ | ○（体は大きく写っている） |
| 顔だけ遮蔽（手・マスク・髪） | ✗ | ○ |
| 極端な寄りで肩が画面外 | ○ | ✗ |
| 人が重なる | ○ | △（骨格が混ざることがある） |
| **暗所・ブレ・小ささ** | ✗ | **✗〜△** |

**最後の行が重要。補完的ではあっても独立ではない。** 暗所・ブレ・小ささは両方を同時に殺す。
C-1 でこれを忘れると危険（7.1 節）。

**頭の箱をつくる（下ほど頑健）：**

1. 頭部キーポイント（鼻・両目・両耳）の外接矩形を拡大する
2. 肩から推定する。肩の中点から、肩を結ぶ線に垂直な方向へ進んだ位置を頭の中心とする
3. 両方が得られたときは両方を描く

**大きさの手がかりの選び方（当初案から修正）：**

人が横を向くと**肩幅は画像上で縮む**（両肩を結ぶ線がカメラを向くため）。横向きこそ
隠したい場面なので、これは放置できない。当初は「胴の長さ（肩の中点↔腰の中点）は
垂直軸まわりの回転で縮まない」を対策としていたが、**これは主用途では使えない**：

- 前傾・後傾、着座、カメラの高さによる短縮では普通に縮む
- **腰が画面に入っていないと計算できない。** この道具の主用途（話している人を撮る）は
  バストショットが中心で、腰は写っていないのが普通

**したがって、実際に効くのは「そのトラックの直近の頭の大きさ」。**
頭サイズを緩やかな状態変数として持ち、不確かなときは単調に大きくする。
胴長の機構を作り込むより、こちらのほうが実装も判断も簡単で堅牢。

**肩線が縮退したときのガード：** ヨーが 90° に近いと両肩がほぼ同じ画像座標に来て、
肩線の方向が数ピクセルの誤差で 180° 回る。**頭を肩の下に置く。**
画素単位の肩幅が閾値を下回ったら、垂線ではなく「画像上の上方向 + 直近の相対位置」に落とす。

**個体較正の自己矛盾（当初案の誤り）：**

「顔検出が成功しているフレームで顔サイズと肩幅の比を実測する」——しかし
**顔検出が成功しているのは正面を向いているとき**であり、その比を適用したいのは
横を向いているとき。**横向きでは肩幅が縮む、というのがこの節の出発点だった。
較正は、直そうとしたバイアスをそのまま継承する。**

較正するなら、対象を回転に強い量（頭サイズ / 頭-肩距離）にするか、
「そのときの肩幅」ではなく時間的に滑らかな深度代理に対して取る。
**較正はクリップを跨いで持ち越さない**（ズーム・カメラ移動・カットで無効になる。
`render.py:236` が区間ごとに tracker を作り直しているのと同じ理由）。

**モデル選定の注意：**

- **旧来の `mp.solutions.pose`（`pip install mediapipe` で最も普通に使われる API）は
  単一人物専用**で、画面内で最も目立つ 1 人しか返さない。多人数には新しい
  `PoseLandmarker` Tasks API を `num_poses > 1` で使う必要があり、**フレーム間の ID 追跡は
  自前**。評価素材に「複数人が交差する」を入れている以上、ここを外すと複数人シーンで
  1 人だけ覆われて残りが素通しになる
- 候補：MediaPipe Pose（導入が軽い）、RTMPose（精度が高いが依存が重い）、
  YOLO 系 pose（AGPL-3.0）。**モデルごとにライセンスが違う**ので「MediaPipe だから
  Apache-2.0」と一括りにしない
- mediapipe は protobuf / numpy をピン留めするので、既存の opencv + numpy 構成と
  衝突しうる。`setup.bat` で 1 発で入る保証はない
- 人物らしい形（ポスター・人形・鏡像）にも骨格が出る。過剰マスクは安全側なので許容

**隠れた工数：** 骨格トラックと顔トラックの対応付け（多人数の跨フレーム ID 管理）が
丸ごと必要になる。これは B-5 本体と同規模の追跡問題。

### B-6 段階的な計算（速度対策）

**安い検出を毎フレーム、高い検出は必要なフレームだけ**に限る。

```
毎フレーム        YuNet（現状のまま）
  ↓ 何も出なかった／トラックが途切れた／確信度が低い フレームだけ
2 段目            解像度を上げる・TTA・アンサンブル
  ↓ それでも出ない
3 段目            頭部検出・骨格推定
  ↓ それでも出ない
                  段階 C へ
```

**前提が成り立つ範囲に注意。** 「大多数は 1 段目で終わる」は簡単な素材でしか成り立たない。
**難しいフレームが 3 割ある素材（＝この計画が対象にしている素材）では、平均コストは
緩和されない。** 2.5 の `detect_every_n_frames` と同じ結合の罠も踏まないこと。

**C-3 との関係：** ラダーの最上段と C-3 の検査器を同じにしてはいけない（7.3 節）。

## 7. 段階 C — 最終防衛線

**「ほぼ 100%」を名乗れるかどうかは、ここで決まる。**

### 7.1 C-1 「人は居るのに顔が無い」フレームを見つける

顔が無いフレームには 2 種類ある。

- **本当に誰も写っていない**（風景・手元・物撮り）→ 何もしなくてよい
- **人は写っているが顔を取れていない** → 危険

**「骨格も顔も無ければ人は写っていない」と判断してはいけない**（当初案の誤り）。
姿勢推定は暗所・強い遮蔽（机の陰で頭と肩しか出ていない座り姿勢＝この道具の主用途）・
フレーム端で半分切れている人・小さい人物・ブレで普通に落ちる。**顔検出と骨格推定は
補完的ではあっても独立ではなく、暗所・小ささ・ブレは両方を同時に殺す**（B-5 の表の最終行）。
両方の陰性を陽性の証拠として扱い、しかも「何もしない」に倒れるのは、この計画の中で唯一
**負の検出結果を根拠に保護を放棄する**箇所だった。

**顔も骨格も無いフレームは「判定不能」とし、C-2 のポリシーに送る。**

**判定材料に音声を使う。** `silence.py` がすでに無音区間を計算している。
**「音が鳴っている（喋っている）のに顔も骨格も無い」は、人が写っている強い証拠。**

- 追加依存ゼロ、計算コストゼロ（既に計算済み）
- **視覚検出器と完全に独立したモダリティ**なので、「検出器の弱点が相関する」問題
  （7.1・7.3 の根本原因）を回避できる唯一の手がかり
- これだけでも、該当区間を最優先の要確認として報告する価値がある

### 7.2 C-2 覆えないフレームの扱い ← 段階 A で実装する

**ぼかし・モザイクは使わない。** 隠すのは `mask.png` の重ね合わせだけで統一する。
したがってここで選べる手は 3 つに絞られる。

```jsonc
"mask": {
  //   expand : 推定できる範囲を大きめに覆う（既定）
  //   cut    : そのフレームを出力から落とす
  //   warn   : 何もせず報告だけする（現状の動作）
  "uncovered_policy": "expand"
}
```

**ぼかしを外すと、漏れ 0 を機械的に保証できるのは `cut` だけになる。**
0 節の「被覆率 100% は設計上到達可能」という主張は、この 1 本で支えることになる。
しかも `cut` は覆っているのではなく、**フレームを出さないことで漏れを消している**。

### 覆えないフレームは 2 種類あり、扱いが違う

| 種類 | 状況 | 扱える手 |
| --- | --- | --- |
| **足場がある** | 直前・直後に検出があり、位置は推定できるが確信が持てない | `expand`。推定範囲を大きめに覆う。**ここは PNG の拡大で足りる** |
| **足場が無い** | そのフレームに検出も骨格も一切無く、位置の手がかりがない | `expand` は**効かない**。広げる対象が存在しない |

**「足場が無い」フレームに対して、ぼかし抜きで打てる手は次の 3 つしかない。**

1. **`cut`** — フレームを落とす。漏れは消えるが、映像から尺が消え、繋ぎ目が飛ぶ
2. **`mask.png` を画面全体に貼る** — 機械的には覆えるが、その 1 フレームは
   絵として完全に失われる。**ぼかしを嫌う理由がそのまま当てはまる**ので、
   選択肢として書いておくだけで既定には置かない
3. **人が直す（A-6）** — `faces_manual.jsonl` に手で箱を書く

**したがって、ぼかしを使わない方針は A-6（手動オーバーライド）の重要度を一段上げる。**
機械が「ここは分からない」と言ったとき、映像を壊さずに解決する唯一の道が人手になる。
実装順序で人手工程（11 節 #6）を C-2（同 #8）より先に置いてあるのは、この意味でも正しい。

実装は「マスクが 1 つも出ていないフレーム」または「推定だけで描いているフレーム」に
対して、箱を広げるかフレームを落とすかを分岐するだけ。`render.py` の 10 行で、
段階 A の時点で書ける。**段階 B に依存させてはいけない。**

### 7.3 C-3 出力の再検査 — 位置づけを訂正する

書き出した `edited.mp4` を再度検出器に掛ける施策。当初「自動 QA として最も価値がある」と
書いたが、**保証できる範囲を取り違えていた。**

**論理的な穴：**

1. **検査器と本番の検出器が同じなら、検査は原理的に空振りする。** フレーム N で本番の
   検出器が失敗したから漏れたのであり、同じ画素を同じ検出器に見せれば同じく失敗する。
   検査の価値は「検査器の再現率 − 本番の再現率」の差分だけ。**B-6 のラダー最上段と
   C-3 の検査器を同じにすると、定義上何も見つからない**
2. **除外ルールが、最頻の漏れ方を握り潰す。** 実務で最も多い漏れは完全な未検出ではなく
   **部分被覆**（箱がずれた・小さかった、2.2 のアルファ、2.1 の端バグ）。部分被覆された顔の
   検出箱は当然マスク位置と重なるので、「マスク位置と重なるものを除外」は
   **部分被覆を狙い撃ちで消す**。隣にいる別人の顔も消える
3. **部分被覆はそもそも顔検出で検知できない。** 目だけ隠して顎と口が出ている顔は
   検出されないことが多いが、人間には誰か分かる。**顔検出は「識別可能性」の代理指標として
   不適切**
4. **検査が何も出さなかったとき、「漏れが無い」のか「検査器が見えていない」のかを
   区別する情報がない**

**保証されること／されないこと（ここを明記する）：**

- **保証される：パイプラインの配管ミスの検出。** 座標変換の取り違え、レターボックスの
  オフセット、A-1 のフレームずれ、`expanded()` の端バグ、マスク PNG の読み込み失敗、
  エンコード段での取りこぼし。**回帰テストとしては優秀**
- **保証されない：検出の再現率に関することは一切。** 「出力に顔が無い」は
  「マスクを貼り忘れていない」以上のことを言わない

**したがって：**

- 位置づけを「被覆率の保証」から**「パイプライン回帰テスト」**に変える。名前も
  `verify` ではなく `selftest` 系にする
- 除外ルールを変える。「マスク位置と重なるものを捨てる」ではなく、
  **重なりが小さい検出＝警告、重なっている検出＝「部分被覆の疑い」として別カテゴリで報告**。
  部分被覆こそ見たいもの
- **検査を顔検出でやるのをやめ、顔認識（埋め込みの距離）でやる**（段階 B 以降）。
  隠したい人物の顔を数枚登録し、出力の各フレームで登録者の埋め込みと一致する領域が
  無いかを見る。これなら「顔検出器は顔と認識しないが人間には識別可能」な部分被覆を
  捕まえられる。**顔認識はトラック結合には不要**（顔が見えている必要があり、
  必要な場面＝後頭部・遮蔽では取れない）だが、この用途には価値がある

## 8. 段階 D — 人の確認を現実的にする

自動で 100% を保証することはできない。**最後は人が見る。**
確認作業を「全編を再生する」から「疑わしい箇所だけ見る」に変える。

- **D-1 コンタクトシート**：危険度の高いフレームを縮小して並べた PNG
- **D-2 確認用の抜き出し動画**：危険な時刻の前後 1 秒だけを繋いだ短い mp4。
  **時刻とフレーム番号を焼き込む**（A-6 の手動オーバーライドを書くのに要る）
- **D-3 検出枠の焼き込み**：マスクの代わりに枠・確信度・**その箱の由来
  （検出 / hold / 補間 / 外挿 / 骨格 / 手動）** を描いた検証用出力。
  **3.2 のアノテーションの下敷きでもあるので、評価基盤より先に作る**
- **D-4 報告の並べ替え**：`edit_report.json` の危険箇所を時刻順ではなく**危険度順**に出す

危険度の目安：判定不能 > 長い外挿 > 骨格からの推定 > 補間 > 確信度が低い検出 > 通常の検出。

### 素顔の中間生成物が新しい漏洩経路になる

- D-1 のコンタクトシート＝**素顔のサムネイルを並べた PNG**
- D-3 の枠焼き込み映像＝**マスクを貼らない素顔の動画**
- 3.2 のアノテーション用出力も同じ
- **`faces.jsonl` 自体が個人情報**（いつ誰がどこにいたかの座標時系列）

プライバシー保護が目的の道具が `output/` に素顔のファイルを生成する。README の運用フローは
「`output\edited.mp4` を確認して人に渡す」なので、`output` フォルダごと渡される。

**確認用の映像・画像は専用のサブフォルダ（`output/_review/`）に隔離し、README に警告を
書き、確認完了後に削除するコマンドを用意する。** ただし **`faces.jsonl` は例外**で、
削除すると「検出は 1 回きり」（9.2）が崩れる。これは `output/` の外（`.tamako_work/`）に
置き、`output/` には人に渡してよいものだけを置く（A-1 の仕様参照）。

## 9. 人が仕上げる工程

**自動で最大限隠し、残りを人が直す。** 100% の自動検出を諦めた以上、これが完成形になる。
この節は、そのために何が要るかをまとめたもの。

**結論から言うと、できる。しかも新しい依存はほぼ要らない。**
必要なものはすでに計画の中に散っており（A-1 の中間ファイル、A-6 のマージ、D の確認用出力）、
それらを一つの作業手順として繋ぐのがこの節の仕事になる。

### 9.1 なぜ今のままではできないか

現状は `tamako edit` が**検出と合成と符号化を一度にやって mp4 を吐く**（`render.py:208-272`）。
人が出力を見て「ここが隠れていない」と気づいても、**その状態に手を入れる場所がない。**
できるのは `config.json` を書き換えて全部やり直すことだけで、しかも直すと別の箇所が
崩れる。これが 1 節の弱点 7（漏れを直す手段が無い）。

**必要なのは、映像と「顔の位置」を分離すること。** A-1 の二段化はそのための布石でもある。

### 9.2 作業の流れ — 修正の確認に動画ファイルは要らない

```
input/*.mp4
   │
   ├─ tamako detect ──► faces.jsonl        自動検出（重い。クリップ並列で 1 回だけ）
   │                                        後処理（max・補間・外挿）もここで済む
   │
   ├─ tamako fix --review ◄────────────┐   窓の中で直す。ドラッグ中に合成結果を
   │      サイトを危険度順に開き、        │   その場で表示（フレームはメモリにあり、
   │      直して、次へ                    │   composite() は数ミリ秒）
   │            │                        │
   ├─ tamako remask ──► _review/*.mp4 ──┘   直したサイトの前後 ±1.5 秒だけを
   │                                        フル解像度で書き出して動きを確認
   │
   └─ tamako edit --final ─► edited.mp4     本番画質で 1 回だけ書き出す
```

**当初案（720p 粗画質で全編プレビュー）は撤回する。** 理由は 2 つ。

1. **粗いプレビューは、最頻の漏れを構造的に見えなくする。** 7.3 で認定した通り、
   実務で最も多い漏れは部分被覆——「顎が数十 px 出ている」「マスクの角の透明部分から
   頬が見えている」。1080p で顔幅 60px は 720p では 40px、そこに `ultrafast` の粗い
   ブロックが乗ると、**顎が 8px 出ているかどうかは原理的に判別できない**。
   プレビューで OK を出し、本番で漏れる。**削ってよい次元は空間ではなく時間**
2. **修正 1 箇所ごとに動画 1 本を再エンコードするのは、人の 1 修正あたり
   18000 フレームの機械作業。** 窓の中でその場合成すれば 1〜30 フレームで済む。3 桁違う

したがって：

- **位置の確認は `fix` の窓の中で即時に**（動画を焼かない）
- **動きの確認は、直したサイトの前後 ±1.5 秒だけを、ソースと同一解像度・`crf 30` /
  `ultrafast` で書き出す**。漏れ 30 箇所でも合計 90 秒ぶん。全編 720p より速く、全部フル解像度
- **本番画質の点検が要るときは `tamako edit --final --only 00:03:10-00:03:20`**（部分書き出し）
- 確認用に**診断モード**を持つ：`mask.png` の代わりにアルファ > 128 の領域をベタ色で塗り、
  頭の推定領域との差分を赤で描く。部分被覆が一目で分かる
- 検出は 1 回きり。本番の書き出しは最後に 1 回。素材から読み直すので何度直しても劣化しない

README の工程は「前半（自動）→ 確認と修正の往復 → 確定 → 後半（字幕）」の 3 工程になる。

### 9.3 操作一式 — 「4 つで十分」は撤回する

当初案の 4 操作（足す・消す・ずらす・確認済み）では足りない。実際のアノテーション・
ロトスコープ支援の運用で必ず要求される操作を含めて、一式はこうなる。

| 操作 | いつ使うか | 備考 |
| --- | --- | --- |
| 足す | 隠れていない顔がある | **1 点で済ませる**：ギャップの前後には自動トラックがあるので、人が 1 点引いたら近傍トラックの動きに沿って伝播させる。2 点要求は工数 2 倍 |
| 消す | 顔でないものを隠している | アンカー参照（9.5）。恒常的な誤検出（ポスター・鏡・人形）は `negative_regions.json` に登録し、**以後の全実行で最初から出さない**（20 行で「消す」操作をほぼ絶滅させられる） |
| **ナッジ・倍率（1 キー）** | 箱が少し小さい・少しずれている——**最頻の修正** | 選択中の箱に `+`/`-`/hjkl で即反映・即再合成。区間一括・トラック一括はこの上位操作 |
| **トラック分割** | 2 人が交差して ID が入れ替わった（`overlay.py` の照合では必ず起きる） | これが無いと「消す」がトラック全体に効き、正しかった前半まで消える。**編集作業で最も頻度の高い構造操作** |
| **トラック結合** | 断片が同一人物だと人が知っている | 繋げば補間で穴が埋まる。A-5 の自動版が失敗したときの唯一の逃げ道 |
| **ホールド延長** | 画面外に出る人をあと 1 秒覆う | A-3 の自動化で大半は消えるが、手動でも 1 操作でできる必要がある |
| **cut に送る** | 機械にも人にも直せない | 「全ての問題は箱で解決できる」わけではない（15 節）。C-2 への手動の導線 |
| **確認済みにする** | 見て問題なかった | 無効化条件は 9.5。**漏れ無し確認と過剰無し確認を区別して記録**する（無効化の向きが逆のため） |
| **undo** | 誤操作 | 追記専用ログ＋操作スタック。**これが無い箱引きツールは実務では使われない** |

### 9.4 何で編集するか — `cv2.selectROI` は使えない

当初案の `cv2.selectROI` は、実際に使うと成立しない。

- **モーダルな独自イベントループを内部で回し、ENTER/SPACE まで返らない。**
  「selectROI で箱を引き、←/→ でコマ送り」は**同一ループに同居できず、実装不能**。
  閲覧と描画の 2 モードになり、箱 1 個ごとにモード切替が入る
- **既存の箱を掴んで動かせない。** 全部ゼロから引き直し。最頻の操作（ずらす）に対して最悪
- ESC が `(0,0,0,0)` を返し「何も引かなかった」と区別できない
- Windows では矢印キーは `waitKey` で取れず `waitKeyEx`＋プラットフォーム固有値が要る。
  窓の × で閉じても検知できず（`getWindowProperty` の監視が要る）、
  `cv2.putText` は日本語を描けない

**`cv2.setMouseCallback` で自前に書く。** マウス処理は実質 40〜60 行で、
selectROI の制約を回避するコードより短い。得られるもの：非モーダル描画、既存箱の
角ドラッグ、任意のキー割り当て（ASCII に割り当てて waitKeyEx 問題を回避）、
そして何より**ドラッグ中にその場で合成結果を表示できる**（9.2 の中核）。

代案として **tkinter（標準ライブラリ）**も検討に値する。Canvas の矩形にはハンドル・
ドラッグ・日本語ラベルが標準で付き、追加依存ゼロで、opencv-python への差し替え判断
（14 節）自体が不要になる。1 週間以上使う道具ならこちらの総コストが低い可能性がある。

いずれでも、**保存先は JSON（`faces_manual.jsonl`）**。窓は入力手段であって、
真実の置き場ではない。全操作にタイムスタンプを打ってログを残す（9.8 の学習データになる）。

```
tamako fix --review               危険度順に、要確認サイトを順に開く（本命）
tamako fix --at 00:03:12          出力時刻で指定して開く（内部では素材 PTS に変換）
```

### 9.5 記録の耐久性 — 「警告を出す」では守れない

**人手記録からトラック ID 参照を無くす。** 当初案は「再検出で ID が崩れたら警告」だったが、
それは**人の 1 時間の作業が警告付きで消えるだけの敗北宣言**なので設計を変える。

- 「消す」「ずらす」は **(clip, PTS 範囲, 素材ピクセル座標のアンカー点)** で記録し、
  適用時に「その PTS 範囲でアンカーから半径 R 以内に中心を持つ箱」に解決する。
  文書のコメントアンカーと同じ方式で、**ID が変わっても、その場所にその人がいる限り
  正しく解決される**。「消す」は本質的に「あそこに出る誤検出を消したい」なので、
  アンカーのほうが意味としても正しい
- `track_id` は内容由来ハッシュ（A-1 のスキーマ）で安定化し、再検出時は旧新トラックを
  時空間 IoU でマッチして `id_map.json` を自動生成する

**確認済みの無効化は「被覆の単調性」で判定する。** 「下の検出が変わったら再確認」を
箱の一致で実装すると、閾値を 0.01 動かしただけで全確認が無効化される。しかも人が設定を
変える動機の大半は安全側（scale を上げる・閾値を下げる）——**最も安全な操作が最も確認を
壊す**という最悪の組み合わせになる。代わりに：

- 確認済みフレームごとに、実際に描いたマスクのアルファ和集合を **32×18 に縮約した
  ビットマップ（72 バイト）**で保存する
- 再実行後、新しい被覆が旧被覆の**上位集合**（覆っていた画素を全部まだ覆っている）なら
  **確認は維持**。被覆が増えるだけなら新たな漏れは原理的に発生しない
- 一部でも減っていれば、**その箇所だけ**再確認

これで「scale を上げた」「閾値を下げた」「箱を足した」は確認を壊さず、壊すのは
「消した」「小さくした」だけになる。**人の作業が保存される条件と、安全性が保証される
条件が一致する。** 過剰無し確認は単調性が逆向きなので種類を分けて記録する（9.3）。

マージ規則は変わらない：人手が常に勝つ、「足す」は自動と union、「消す」は明示的な否定。

### 9.6 レビューの順番 — サイト順ではなくトラック順

- **最初に「全体倍率スイープ」を 1 回。** scale 2.0 / 2.4 / 2.8 で数フレームだけ合成して
  見せ、1 つ選ばせる。これだけで残りサイト数が半減することが普通にある。個別修正より先
- **導線は「トラック一覧（危険度順）→ そのトラックのサイト」の 2 階層。**
  1 本のトラックがずっと小さいなら、トラック一括倍率で配下の 10 サイトが一度に消える。
  サイト順に流すと同じ修正を 10 回することになる
- **同種の問題をまとめて出す。** `source`（由来）でグルーピングし、同じ操作で片付くものを
  連続で処理させる。モード切替コストが消える
- **無作為監査枠 5%。** 危険度に関係なく 5% のサイトを必ず提示する。見逃し率（3.1）の
  推定はここでしか得られず、これが無いと 9.8 の学習が「人が見なかった箇所は安全」という
  自己強化に陥る

### 9.7 作業時間の予算 — 30 分に収める

当初案の設計（selectROI＋全編プレビュー往復）で「10 分の動画・漏れ 30 箇所」を見積もると：
トリアージ 50 分（畳んでいない危険リスト数百件の選別）＋修正 45〜120 分＋プレビュー
再書き出し 15 分〜2 時間＋最終目視 20〜30 分 = **合計 2.5〜4 時間**。
`.bat` をダブルクリックする層の道具として成立しない。

**目標は 30 分以内**。そのための設計が本節の内容そのもの：

| 施策 | 削減 |
| --- | --- |
| その場合成（9.2）— プレビュー往復の廃止 | 最大 2 時間 |
| サイト集約＋有効指摘率 0.5 以上（3.1） | 約 40 分 |
| 最頻修正の 1 キー化（9.3） | 約 20 分 |
| 足すの 1 点化（9.3） | 約 15 分 |

そして**設計上の上限を置く**：後処理後の提示サイト数が **50 件/10 分**を超えるなら、
人に渡す前に自動側（scale・閾値・max フィルタ幅）を直すのが先。人手工程が成立する
境界を数値で決めておかないと、「まず自動、残りは人」という分担が破綻に気づけない。

### 9.8 人手工程は評価装置でもある

`tamako fix` が自動で記録するログ——10 分あたりの修正操作数、操作の内訳、サイトあたりの
所要秒——は、**1000 フレームの評価セットより広い範囲（実素材の全編）を測っており、
決定に直結し、コストがゼロ**。

- 修正の 8 割が「箱が小さい」なら → 答えは段階 A/B ではなく 0-2 のアルファ補正の詰め
- 修正の 8 割が「後頭部」なら → **そのとき初めて** B-5 と評価素材の撮影・アノテーションに
  投資する判断ができる
- B-5 の効果測定も「入れて修正回数が減ったか」で足り、頭アノテーションを人質に取られない

**危険度の較正もここから作る。** サイトごとの特徴量（ギャップ長・前後速度の食い違い・
由来・スコア・画面端距離・輝度・ブレ・音声エネルギー・頭サイズ変化）に対し、
目的変数「人がそのサイトを修正したか」をロジスティック回帰 1 本で学習する（50 行・依存ゼロ）。
危険度順が「感覚の順序」から「較正された確率」になり、有効指摘率がそのまま検証指標になる。
生の検出スコアは「人が直す必要があるか」の代理として不適切（2.5 の `low_confidence` 爆発が
その証拠）。**必須のガード：9.6 の監査枠**。修正ログだけで学習すると見落としが自己強化される。

修正の再利用は**プロジェクト単位**で持つ（グローバルには持たない）：
レビューを通過した scale / 閾値、恒常的誤検出領域（`negative_regions.json`）、較正係数。
同じ人・同じ部屋・同じカメラが繰り返し出る素材でだけ効く。

### 9.9 これで何が変わるか

- 漏れへの対処が「設定を変えて全部やり直す」から「**その箇所だけ、その場で直す**」になる
- 確認が「毎回全編」から「**変わったところ＋監査枠だけ**」になる
- `mask.png` 以外の隠し方（ぼかし等）を足す必要がなくなる
- 人手工程のログが、段階 B への投資判断の材料になる（9.8）
- 15 節の限界は変わらない。**「見なくてよい」にはならない。** 見て、見つけて、
  直せるようになるだけで、最後の全編目視は残る

## 10. 素材側の運用ルール

**ROI で言えばこれが単独最大で、コストはゼロ。**
アルゴリズムで取り返そうとしている損失の多くは、撮影段階で作られている。

- **シャッタースピードを上げる。** モーションブラーが減り、YuNet の再現率が直接上がる
- **逆光を避け、顔に光を回す**
- **撮影解像度を上げる。** 4K で撮って 1080p に落とせば、検出は 4K 側で走らせられる
- **背景に通行人が入る画角を避ける**
- 自分たちの撮影なら、被写体に「カメラに背を向けない」「顔を手で覆わない」と伝える

エンジニアリング計画としては範囲外だが、目的（顔を隠す）に対しては最も効く。

## 12. 速度への影響

まず、以前の記述の訂正：**A-1 の二段化で復号は増えない**（A-1 の節を参照。
`fps=` フィルタは復号を間引かないため、現状すでにフルレート復号は 2 回走っている）。

**予算の骨格を先に置く。** 数値はオーダーの見積りで、11 節 #3 の実測で置き換える。
10 分 1080p30 = 18000 フレーム、中位の 4 コア Windows ノートを想定：

| 工程 | スループット | 10 分素材の所要 |
| --- | --- | --- |
| H.264 復号 1080p | 200〜400 fps | 1〜1.5 分 |
| YuNet @ 640 幅 | 100〜200 fps | 1.5〜3 分 |
| YuNet @ 1280 幅（0-5 の推奨値） | **25〜50 fps** | **6〜12 分** |
| H.264 符号化（preset medium / crf 20） | 30〜60 fps | 5〜10 分 |

ここから直ちに分かること：

- **`detect_width: 1280` にした時点で、検出が符号化と並ぶ最大コストになる。**
  「YuNet は軽い」は 640 のときの話。**クリップ単位の並列化（A-1 の設計項目）が
  予算を閉じる前提**であり、逃げ道ではない
- **B-2 の TTA（3〜5 倍）や B-3 のアンサンブル（2〜3 倍）を全フレームに掛けると
  20〜60 分。** B-6 のラダーで**上位段を全フレームの 10% 未満**に抑えられない素材
  （難所が 3 割ある素材）では、**B-2/B-3 は採らない**——これを B-6 の設計制約として明記する
- バッチ時間と別に**対話時間**（3.1）がある。人の修正 1 箇所あたりに機械が待たせる
  時間は数秒以内。9.2 のその場合成が前提

残りの逃げ道：onnxruntime の GPU 対応（Windows なら DirectML）、`preset` を落とす。

## 13. 設定の追加案

**素の設定項目を増やしすぎると破綻する。** 現在 `mask` は 7 項目で、下の案を全部足すと
18 項目。しかも `detect_scales` × `rotation_tta` × `detectors` はコストが掛け算で増え、
`pose_calibrate` は `pose_fallback` に依存し、`uncovered_policy` は他の全部の結果に依存する。
**README がバッチファイルをダブルクリックする層に向けて書かれている**ことを考えると、
この設定面は使われない。

**プリセットを 1 つだけ表に出す。**

```jsonc
"mask": {
  // normal   : 現状相当
  // high     : 閾値低め・解像度高め・補間あり（推奨）
  // paranoid : 覆えないフレームを出力から落とす。確実だが尺が削れる
  "safety": "high"
}
```

## 14. 決めておくべきこと

1. **依存を増やしてよいか**。段階 B の効果は大きいが、`setup.bat` が重くなり、
   ネットワークが塞がれた環境での導入が難しくなる。現状は OpenCV と numpy だけで完結している。
   **11 節の #1〜#9 は追加依存なし（`fix` の窓の GUI ビルド判断のみ）で完結する**ので、
   この判断は先送りできる
2. **モデルのライセンス**。配り方（個人利用か、公開か、業務か）で使えるモデルが変わる。
   B-3・B-5 の注意書きを参照。**モデル単位で確認する**こと
3. **後頭部・真横を隠す必要があるか**。素材にそれが出るなら B-5 が要る。
   判断材料は 11 節 #9 の実測（修正の内訳に「後頭部」がどれだけ出るか）。
   効果測定も「入れて修正回数が減ったか」で足りる（9.8）ので、
   アノテーションを先に済ませる必要はない
4. **過剰マスク率の上限**（3.1 の制約）。顔以外が隠れて映像が成立しなくなる線。
   これを数値で決めないと、指標系が全画面ブラーに向かって退化する
5. **処理時間の上限**。10 分の 1080p を Windows の CPU 単体で何分までなら許容するか。
   B の積み上げは 12 節の予算表から逆算する。対話時間は別枠で、
   人の修正 1 箇所あたり数秒以内（9.2 のその場合成が前提）
6. **`fix` の窓を何で出すか**（9.4）。`opencv-python-headless` を通常版に差し替えるか
   （同じ opencv の別ビルド、`setup.bat` の変更のみ）、tkinter（標準ライブラリ・
   追加依存ゼロ・部品が揃っている）にするか。1 週間以上使う道具なら tkinter が有利
7. **人手工程の成立条件**。提示サイト数の上限（既定 50 件/10 分）と、
   1 本あたりの人手作業時間の目標（既定 30 分）。11 節 #9 の実測後に見直す
8. **カット判定への波及**。顔検出の再現率を上げると `cut.mode: any` での「顔なし」判定が減り、
   カットされる区間が減る（`pipeline.py:68-79`）。閾値は分離されているが
   **`detect_width` は分離されていない**（2.3）。カットは false positive が困り、
   マスクは false negative が困る、という非対称を設定の分離で保つ

## 15. この計画の限界

段階 D まで実装しても、**「見なくてよい」とは言えない**。言えるようになるのは
「見るべき箇所が全長の数 % に絞られ、そこを見れば足りる」までで、README の警告は残す。

C-2 で `cut` を選べば漏れフレームは定義上ゼロになるが、それは
「顔が写っているかもしれないフレームを捨てた」だけで、検出できたわけではない。
確実性と映像の質は交換関係にあり、この計画はその交換を**人が選べる形にする**もので、
交換そのものを無くすものではない。

**ぼかし・モザイクを使わない方針は、この交換条件を一段厳しくする。**
ぼかしは「絵は汚れるが尺は残る」という中間の妥協点だった。それを外すと、
残るのは「尺を捨てる（`cut`）」か「人が直す（A-6）」の二択になる。
どちらも取れない箇所は、**報告して人の目で確認するしかない**。

そして、**3.3 で書いた通り、評価セットは「漏れ 0」を証明できない。**
証明できるのは「難所での漏れ率が下がった」ことまで。
「漏れ 0」は C-2 の機械的な処置と、A-6 の人手修正と、最後の目視が担保する。
評価で 0 だったことを、出荷して安全だと読み替えないこと。

**9 節の仕上げ工程を入れても、この限界は動かない。** 変わるのは、漏れを見つけたときに
できることが「全部やり直す」から「そこだけ直す」になり、確認が「毎回全編」から
「変わったところだけ」になること。**見なくてよくなるのではなく、見て直せるようになる。**
最後に全編を目で通す必要は残る。
